# Kibo · Phase 25 : Kibo, outil de suivi — fonctionnalités, sprints et suivi git Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Kibo devient un **outil de suivi de projet** (décisions d'Adam du 2026-10-16, spec **§37**). Le développement se fait dans T3 Code avec le skill `full-delivery` ; Kibo **observe** : la création de la branche d'un ticket le passe *En cours*, la PR ouverte *En review*, la PR fusionnée *Terminé*, sans token. Une **fonctionnalité** est un ensemble (§36) dont les étapes sont ses sous-tickets ordonnés ; on la livre de A à Z. Un **sprint** est un objet (nom, dates) ; une fonctionnalité lui est assignée dans le **Planning** (colonnes par sprint, réserve « À planifier », glisser pour planifier). Règles dérivées : *ouverte* (au moins une étape commencée), *livrée* (toutes les étapes obligatoires terminées ; la démo client est facultative), *en retard* (le sprint est fini et il reste des étapes), limite d'ouvertes en **avertissement** (2 par défaut, réglable par projet). L'exécution des agents dans Kibo est **masquée derrière un réglage**, pas supprimée ; l'agent de projet reste. Écrans de cette phase : **P2 Planning**, **P3 fiche fonctionnalité**, **P4 Tickets** (P1 bis Vue d'ensemble et P5 Graphe en phase 26), en sombre et en clair, **au pixel près** d'après `design/redesign/exports/`.

**Architecture:** tout le neuf est **déterministe** : une branche vue dans `refs/`, une PR lue par `gh`, une étape posée par `kibo tickets step`, un glisser dans le Planning sont des événements ; aucune parole d'agent ne change un état. `schema` porte les contrats (`Sprint`, `Ticket.sprintId`, `Ticket.optional`, `Ticket.shortKey`, `TrackingSettings`, règle `branch_created`, `AppSettings`, commandes, entité `sprint`) et les fonctions pures (`featureState`, `sprintState`, `nextFeature`, `matchBranchToTicket`) ; `core` applique les commandes, alloue les clés courtes, dérive les vues avec une date injectée ; le démon observe les branches (`git for-each-ref`, sans réseau), relie l'observateur au poller des PR (§23.6), stocke le réglage local, joue les migrations ; la CLI déclare la branche (`kibo tickets set branch=`) ; l'interface ajoute le composant intégré **Planning** (vue), la fiche fonctionnalité, les colonnes Git et Livraison de Tickets, le réglage « Exécution des agents ». **Acceptation pixel** : chaque écran est capturé par Playwright au viewport de la maquette (1440 px, même hauteur), sur la **fixture « Emis maquettes »** (horloge figée au 16 octobre 2026), et comparé au PNG de `design/redesign/exports/` ; l'image de différence est fournie, le seuil est **≤ 2 % de pixels différents** (`maxDiffPixelRatio: 0.02`, tolérance par pixel `threshold: 0.3`) ; **le reviewer refuse toute tâche d'UI sans image de différence sous le seuil**.

**Tech Stack:** Bun, TypeScript strict, Zod, Loro, SQLite (`kibo.db`), React + shadcn/ui + Tailwind, Playwright 1.55 (`toHaveScreenshot`, `page.clock`), fast-check, Biome, faux `gh`, dépôts git temporaires. Base : `phase/25` créée depuis `main` (v0.24.0-alpha.4) ; branches `feat/p25-t<n>`, worktrees `.claude/worktrees/p25-t<n>`. Les maquettes officielles sont mises à jour en parallèle sur `design/redesign` par l'agent des maquettes : l'UI s'appuie sur `design/redesign/exports/` et sur `design/redesign/cotes.md` (fourni par lui).

## Global Constraints

- **Zéro token pour l'état** : branche (`refs/`), PR (`gh`), étape (`kibo tickets step`), sprint (commande), report (clic) ; l'agent de projet **propose** (phase 26), Adam valide.
- **Local-first, sans réseau nouveau** : l'observateur de branches lit les refs locales (`refs/heads`, `refs/remotes`) du dossier du projet, jamais `git fetch` ; les PR restent au poller existant.
- **Date injectée** : aucune fonction de `schema` ou de `core` n'appelle `Date.now()` ; `today: string` (`YYYY-MM-DD`, fuseau de la machine) vient du démon (`clock`), et le démon honore `KIBO_FIXED_NOW` (E2E seulement, journalisé au démarrage). L'interface ne calcule aucun état de sprint : elle lit `SprintView.state`.
- **Masquer, pas supprimer** : le réglage `agentExecution` cache les entrées Agents / Files d'attente / Skills, la barre et le volet, « Assigner » et « Livrer » (remplacé par « Copier `/full-delivery <CLÉ>` ») ; la file, les runs, les questions, l'agent de projet et les RPC continuent ; `shown` rend tout.
- **Pureté et tailles** : `schema` sans dépendance hors `zod` ; `core` sans I/O ; fichiers kebab-case, exports nommés, **aucun commentaire**, < 300 lignes ; `AppSidebar.tsx` (274 l.) ne grandit pas : l'entrée Planning et le masquage passent par de petits composants ; `GroupDetail.tsx` devient `FeatureDetail.tsx` + sous-composants.
- **Pixel** : chaque tâche d'UI (T8, T9, T10, T11) livre, pour chaque écran qu'elle touche, `screens/2026-10-<jj>-t<n>/<écran>-{dark,light}.png` **et** `<écran>-{dark,light}-diff.png`, prises par `e2e/pixel-kit.ts` (viewport 1440 × hauteur de la maquette, `page.clock.setFixedTime("2026-10-16T14:52:00+02:00")`, fixture T2, `document.fonts.ready`, `animations: "disabled"`, `caret: "hide"`), comparées au PNG de `design/redesign/exports/` (`snapshotPathTemplate` pointé sur ce dossier, `updateSnapshots: "none"` : la référence n'est **jamais** réécrite par un test) ; seuil **`maxDiffPixelRatio: 0.02`**, **`threshold: 0.3`**. Justification du seuil : le rendu du texte de Penpot et celui de Chromium diffèrent sur les bords anticrénelés (mesuré sur la phase 24 entre deux moteurs : 0,8 à 1,4 % des pixels d'un écran dense) ; 2 % n'absorbe aucun décalage de bloc (une ligne de 40 px décalée sur 1440 px vaut 5,8 % d'un écran de 1000 px). **Le reviewer refuse toute tâche d'UI sans image de différence sous le seuil.**
- **Budget UI** : exigence de la phase **≤ 224 000** octets gzip (mesure de départ en T0 ; plafond 230 000 jamais relevé). L'entrée gagne : les champs `sprintId`, `optional`, `shortKey` du ticket, le schéma `Sprint`, `AppSettings`, le manifeste du composant Planning (registre), l'icône `CalendarRange`, la lecture du réglage dans la coque. Tout le reste est différé et cité dans `FORBIDDEN_IN_ENTRY` : `components/planning/**` (hors manifeste), `ui/src/tracking/**`, `i18n/fr-tracking.ts`, `shell/FeatureDetail.tsx`, `dialogs/{SprintDialog,NewFeatureDialog}.tsx`.
- **Polices** : Geist et Geist Mono (OFL 1.1) embarquées dans `packages/ui/public/fonts/` et déclarées par `@font-face` (T1) ; aucune dépendance npm nouvelle, aucun appel réseau.
- **Tests sans token** : dépôts git temporaires (`git-test-kit`), faux `gh`, horloge injectée, fast-check ; aucun test n'écrit hors de `tmp()`.
- Git : branche `feat/p25-t<n>` depuis `phase/25`, worktree `.claude/worktrees/p25-t<n>` ; commits d'une ligne en français, préfixe conventionnel, **< 50 caractères** (`wc -m`), fichiers stagés explicitement, aucune mention d'IA. `bun run check && bun run typecheck && bun test packages components` verts avant chaque commit final ; `bun run budget` pour T8 à T13.

## Décisions d'exécution

1. **Sprints dans le CRDT** : map Loro `sprints` du doc projet, une entrée par `sprintId` (valeur `Sprint` JSON) : deux créations concurrentes fusionnent ; l'ordre d'affichage est `start` puis `name`. Lecture `listSprints(doc)` dans `core/src/sprints.ts` ; `ProjectSnapshot.sprints: SprintView[]` (défaut `[]`).
2. **Fonctionnalité** = ensemble **racine** (`parentId === null && isGroup`) ; `isFeature(view)` dans `schema/src/feature.ts`. Un ensemble imbriqué est une étape à sous-étapes (son avancement propre), sans clé courte ni sprint.
3. **Étapes** = `deliveryOrder` (§35.3) restreint aux **enfants directs** (un ensemble imbriqué est une étape, pas développé) : `featureSteps(feature, tickets, links)` dans `schema/src/feature.ts`, réutilise la topologie de `delivery-order.ts` (fonction interne extraite `topoByBlocks`).
4. **Clé courte** : `Ticket.shortKey` (`^[A-Z]{1,3}[0-9]{1,3}$`, unique par projet), allouée dans `core/src/commands.ts` par `createTicket`/`moveTicket` quand une **racine** gagne son premier enfant (`meta.featureSeq`, préfixe `F`), modifiable par `updateTicket.shortKey` ; la migration de T6 pose le `plan:<ID>` quand il passe la regex, sinon `F<n>` par rang.
5. **Facultatif** : `Ticket.optional: boolean` (défaut `false`), commande `setTicketOptional { ticketId, optional }` (`COMMAND_WRITES = "ticket"`), permise sur un ticket **avec parent** seulement ; `groupStatus`, `children_done` et `featureState.delivered` ignorent les facultatifs ; `progress` compte tout (« 4/5 · livrée » affiche « démo à faire »).
6. **Observateur** : `daemon/src/tracking/branch-observer.ts`, appelé par le `tick` du poller des PR (même cadence, `pollMs`) **et** au changement de signature du `worktree-watch` ; lit `git for-each-ref --format=%(refname:short) refs/heads refs/remotes` dans `project.folder` (préfixe `origin/` retiré), compare à la signature précédente, puis pour chaque branche : ticket par `git_branch` déclaré, sinon `matchBranchToTicket(branch, tickets)` (clé entre bornes `(^|[^A-Za-z0-9])<KEY>([^0-9]|$)`, casse ignorée, **un seul** candidat) ⇒ `upsertExternalRef git_branch` d'origine `kibo` ; puis `triggerRules(branch_created)` pour les tickets qui portent une branche existante et sont en `backlog|todo`. Jamais de `fetch`.
7. **Règle `branch_created`** : `Rule.when` gagne `branch_created` ; `DEFAULT_RULES` gagne `{ id: "branch-created-in-progress", when: "branch_created", from: [backlog, todo], to: in_progress }` ; `readRules` complète une liste stockée qui n'a pas cet `id` (`withDefaultRules`, pure, idempotente). La règle `run_started` reste (exécution montrée).
