# Kibo · Phase 10 : suivis après v1.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** fermer les suivis techniques nés de la phase 9 et du jalon v1.1 (passation du 2 octobre, rapports de jalon et de vagues 3 et 4) sans ouvrir de chantier fonctionnel : un seul démon par `KIBO_HOME` et une coque qui réagit proprement, des causes d'échec de run lisibles, les alertes Dependabot traitées, les transactions SQLite en mode `immediate`, le contrôle d'écriture avant la mise en file, la durée d'un run sans le temps mort, le délai du contrôle de types nommé, les petits défauts d'accessibilité et d'aperçu, le durcissement des routes, le test de démarrage de la coque dans la gate locale, deux fichiers ramenés sous ~300 lignes, la propriété de `planLayoutSave` rejouée sur les vraies règles, et l'écriture à un agent pendant son tour. Aucun token consommé, budget de chargement initial jamais relevé, maquettes Penpot hors périmètre (traitées à part).

**Architecture:** presque tout est du démon et du cœur. Le démon gagne une sonde de démarrage (`single-instance.ts`), une route `GET /api/health`, deux lignes de protocole sur sa sortie standard (`KIBO_REUSED`, `KIBO_FATAL`) que la coque Tauri interprète (fenêtre sur le démon en place, ou boîte de dialogue native) ; `prepareWorkspace` nomme ses causes d'échec ; les transactions qui lisent puis écrivent passent par un unique `immediateTransaction` par paquet ; l'orchestrateur contrôle l'écriture avant la file et se découpe ; la machine à états des runs gagne deux champs dérivés (`activeMs`, `turnStartedAt`) et un événement `requeued` ; le devkit émet son rapport statique par étapes. L'interface change peu : quatre textes d'erreur, `elapsed`, la zone de saisie du tiroir pendant un tour, deux `h1` en moins, l'aperçu d'un brouillon mis à l'échelle, `Shell.tsx` découpé.

**Tech Stack:** Bun 1.4.2, TypeScript 5.9 strict, Zod 3.25.76, React 19 + shadcn/ui, Vite **7.3.5** (mis à jour par T4, depuis 7.1.6), markdown-it **14.3.1** (T4, depuis 14.1.0), happy-dom + Testing Library, fast-check 4.3.0 (déjà présent dans `packages/ui`), Playwright, Tauri 2 (`tauri-plugin-dialog` 2.8 déjà dans `Cargo.lock`, `DialogExt::dialog().message().blocking_show()`), cargo 1.98 local (`~/.cargo/bin/cargo`).

**Spec:** `docs/superpowers/specs/2026-09-25-kibo-design.md` **§17** (décisions de la phase 10, écrites avant ce plan : un seul démon par `KIBO_HOME`, transactions `immediate`, durcissement des routes, gate et coque, codes d'erreur, alertes de sécurité), §15.3 (écran « Kibo ne répond pas », message d'arrêt de la coque) ; `docs/superpowers/specs/2026-09-26-kibo-agents.md` **§14** (causes d'un run échoué, durée affichée, ordre des contrôles d'`assignAgent`, message pendant un tour, attente de verrou), §3, §4, §6, §8, §13 ; `docs/superpowers/specs/2026-09-26-kibo-composants.md` §7.4 et **§17 point 7** (délai du contrôle de types, rapport par étapes), §16 point 8 (`daemon.json`), §17 point 6 (CSP du worker). Sources des suivis : `docs/superpowers/rapports/2026-10-01-passation-phase-9.md`, `2026-10-01-jalon-v1.1.md`, « Risques et suivis » de `2026-10-01-phase-9-vague-3.md` et `2026-10-01-phase-9-vague-4.md`.

## Review Focus

1. **Deux démons, même dossier** (T1) : le second ne crée ni n'ouvre `kibo.db`, `runs.db`, ni n'écrit `daemon.json` (le fichier garde le pid et les ports du premier) ; `startDaemon` rejette `DAEMON_RUNNING` ; un `daemon.json` dont le port ne répond pas (connexion refusée) laisse démarrer ; un port qui accepte la connexion sans répondre refuse en ≈ 1 s, jamais plus de 2 s.
2. **Protocole de sortie** (T1, T2) : `KIBO_REUSED` est suivi des deux lignes `KIBO_READY` / `KIBO_SANDBOX` **du démon en place** (jeton du fichier `token`, ports de `daemon.json`), code de sortie 3 ; `KIBO_FATAL <code> <détail>` tient sur une ligne et précède la sortie 1. Côté coque : après `KIBO_REUSED`, `Terminated` n'est pas une panne et aucun `kill` n'est envoyé à la fermeture ; `KIBO_FATAL` affiche la boîte (hors `KIBO_SMOKE`) puis quitte 1.
3. **Causes d'échec** (T3) : chaque cause de `prepareWorkspace` a son code et un test ; `WORKSPACE_FAILED` ne reste que pour les deux défauts internes ; la notification, l'historique et le journal montrent le même texte français.
4. **Mises à jour** (T4) : `bun.lock` ne change que pour `vite`, `markdown-it` et leurs transitives ; `bun install --frozen-lockfile` passe ; `bun run build` de l'UI émet toujours le worker sous `workers/` et le budget tient ; l'alerte `glib` est rejetée avec motif, pas ignorée.
5. **`immediate` partout** (T5) : le test de garde liste les fichiers de la spec §17.2 ; le test de comportement prouve qu'une connexion concurrente échoue en `SQLITE_BUSY` pendant la transaction et qu'une transaction différée perdrait l'écriture (`SQLITE_BUSY_SNAPSHOT`).
6. **Rien en file après un refus** (T6) : `assign` sur un projet en lecture seule jette `FORBIDDEN` et `state().runs` reste vide ; un échec d'`assignTicket` ne met rien en file ; l'ordre des événements d'un `assign` réussi est inchangé pour le reste (`enqueued` puis `tick`).
7. **Durée** (T7) : un run avec deux tours séparés par une heure d'attente affiche la somme des deux tours ; en cours de tour, la durée avance ; en `waiting_input` ou `queued`, elle n'avance pas ; un run jamais démarré affiche « - ».
8. **Message pendant un tour** (T13) : le message est journalisé aussitôt, le tour en cours n'est pas touché, le tour suivant démarre dès la sortie du processus avec les messages en attente (dans l'ordre, séparés par une ligne vide) comme prompt ; `cancelled` et `failed` effacent l'attente ; un run sans ticket refuse toujours hors `waiting_input` ; `requeued` n'apparaît jamais dans le journal du tiroir.

## Décisions

Les décisions de démon, de coque, de données et d'agents sont écrites en spec de conception §17, spec agents §14 et spec composants §17 point 7 ; le plan ne les répète pas. Décisions d'exécution prises par ce plan, à reporter au rapport de phase :

1. **Sonde par HTTP, pas par signal.** Vérifier qu'un pid est vivant (`process.kill(pid, 0)`) ne suffit pas (pid réattribué) et ne dit pas si le démon répond ; la sonde `GET /api/health` tranche les trois cas (rien n'écoute, répond, muet) de façon déterministe. La sonde vit dans `packages/daemon/src/single-instance.ts`, injectable (`probe`) pour les tests.
2. **Le démon décide, la coque affiche.** Toute la logique de réutilisation (lecture de `daemon.json`, du jeton, choix du code de sortie) reste dans le démon ; la coque Rust ne fait qu'interpréter trois lignes (`KIBO_REUSED`, `KIBO_READY`, `KIBO_SANDBOX`) plus `KIBO_FATAL`, pour garder le Rust minimal et testable par des fonctions pures.
3. **`DaemonRunning` est une `KiboError`** (code `DAEMON_RUNNING`) qui porte le démon trouvé (`running: { info, answers }`) : `main.ts` l'utilise sans relire le disque. Le code reste stable pour la CLI et les scripts.
4. **Un helper par paquet pour les transactions** : `immediateTransaction(db, fn)` dans `packages/daemon/src/sqlite-busy.ts` et dans `packages/sync-server/src/db.ts` (quatre lignes, dupliquées : `sync-server` ne dépend pas du démon et `schema` n'a pas `bun:sqlite`). `store.transaction` et la création d'un run l'adoptent aussi pour que le test de garde soit uniforme.
5. **`AgentDataPort.assertWritable(projectId)`** plutôt qu'un contrôle dans `agents-rpc.ts` : l'orchestrateur est le seul endroit qui connaît l'ordre « contrôles, écriture du ticket, mise en file », et les tests de l'orchestrateur le vérifient sans démon.
6. **Durée dérivée, pas stockée** : `activeMs` et `turnStartedAt` sont calculés par `reduceRun` ; aucun événement nouveau, `runs.db` inchangé, les anciens journaux se relisent.
7. **Rapport statique par étapes (NDJSON)** : une ligne JSON par étape (`imports`, `typecheck`, `inference`) ; le parent assemble et complète ce qui manque à l'expiration. Nouveau code d'issue `inference-skipped` dans `SourceIssueCode` (énumération fermée, donc explicitement ajoutée).

```ts
import { KiboError } from "@kibo/schema";
import { type DaemonInfo, readDaemonInfo } from "./components/daemon-info";

export type HealthAnswer = { pid: number } | "refused" | "silent";
export type Probe = (port: number) => Promise<HealthAnswer>;
export type RunningDaemon = { info: DaemonInfo; answers: boolean };

export const HEALTH_TIMEOUT_MS = 1_000;

const isTimeout = (e: unknown): boolean => e instanceof Error && e.name === "TimeoutError";

const pidOf = (body: unknown): number | null => {
  const pid: unknown = typeof body === "object" && body !== null ? Reflect.get(body, "pid") : null;
  return typeof pid === "number" && Number.isInteger(pid) && pid > 0 ? pid : null;
};

export const probeHealth: Probe = async (port) => {
  let res: Response;
  try {
    res = await fetch(`http://127.0.0.1:${port}/api/health`, { signal: AbortSignal.timeout(HEALTH_TIMEOUT_MS) });
  } catch (e) {
    return isTimeout(e) ? "silent" : "refused";
  }
  if (!res.ok) return "silent";
  const pid = pidOf(await res.json().catch(() => null));
  return pid === null ? "silent" : { pid };
};

function readInfo(home: string): DaemonInfo | null {
  try {
    return readDaemonInfo(home);
  } catch (e) {
    if (e instanceof KiboError && e.code === "STORE_CORRUPT") return null;
    throw e;
  }
}

export async function findRunningDaemon(home: string, probe: Probe = probeHealth): Promise<RunningDaemon | null> {
  const info = readInfo(home);
  if (!info) return null;
  const answer = await probe(info.port);
  if (answer === "refused") return null;
  return { info, answers: answer !== "silent" };
}

export class DaemonRunning extends KiboError {
  constructor(
    readonly home: string,
    readonly running: RunningDaemon,
  ) {
    const where = `http://127.0.0.1:${running.info.port}`;
    super(
      "DAEMON_RUNNING",
      running.answers
        ? `another daemon (pid ${running.info.pid}) serves ${home} at ${where}`
        : `another daemon (pid ${running.info.pid}) holds ${home} at ${where} and does not answer`,
    );
    this.name = "DaemonRunning";
  }
}
```

```ts
import { sameRunToken } from "./run-token";

export type HookSinkDeps = { live: Map<string, LiveRun>; tasks: Map<string, TaskSpec>; registry: RunRegistry };

export function createHookSink({ live, tasks, registry }: HookSinkDeps): HookSink {
  return {
    verify(runId, token) {
      const entry = live.get(runId);
      return entry !== undefined && sameRunToken(token, entry.hash);
    },
    receive(runId, payload, toolInput) {
      registry.apply(runId, { type: "hook", payload });
      const guard = tasks.get(runId)?.guard;
      if (!guard || payload.event !== "PreToolUse") return null;
      try {
        return guard({ tool: payload.tool ?? "", input: toolInput ?? null });
      } catch (e) {
        console.error(`[kibo-daemon] guard of run ${runId} failed, denying`, e);
        return { decision: "deny", reason: "guard error" };
      }
    },
  };
}
```

```ts
import { existsSync, readFileSync } from "node:fs";
import { join } from "node:path";

export function recordedPid(home: string): number | null {
  const file = join(home, "daemon.json");
  if (!existsSync(file)) return null;
  try {
    const pid: unknown = Reflect.get(JSON.parse(readFileSync(file, "utf8")), "pid");
    return typeof pid === "number" ? pid : null;
  } catch (e) {
    if (e instanceof SyntaxError) return null;
    throw e;
  }
}

export function isAlive(pid: number): boolean {
  try {
    process.kill(pid, 0);
    return true;
  } catch (e) {
    if (e instanceof Error && "code" in e && e.code === "ESRCH") return false;
    throw e;
  }
}

export function smokeCommand(binary: string, platform: NodeJS.Platform): string[] {
  return platform === "linux" ? ["xvfb-run", "-a", binary] : [binary];
}
```
