# Kibo · Phase 20 : Voir et comprendre ce que font les agents Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** rendre visible le travail des agents, sans un token de plus pour l'état : un **fil narratif** par run, tiré de la transcription Claude Code (phrases de l'agent, actions repliées en français courant, détail technique au dépli), copié dans `runs.db` ; un **plan** et un **compte rendu** tenus par l'agent par l'outil MCP `ticket_progress`, portés par le ticket (CRDT) et repris d'un run à l'autre, avec rappels sans blocage et repli sur `TodoWrite` ; une **barre du pied de page** entièrement cliquable et redimensionnable, un **volet** en trois colonnes, un onglet **Activité** sur la fiche, des **mentions d'agent** cliquables (carte, volet, page dédiée) ; la page **Questions** refondue avec des **destinataires** par projet, l'export et la réponse collée ; l'état calculé **« démarrable »** ; et un **graphe lisible** (vagues, terminés repliés, liens réduits, focus, zoom sémantique, couleur du statut, regroupement par étiquette).

**Architecture:** `schema` (moments, libellés, masquage, progression, destinataires, démarrable, RPC, appel `run.peek`, cible `run`) → `core` (analyse de transcription et pliage en moments, purs ; commandes de progression et de destinataires ; `readProject` avec l'activité des runs ; consignes) → `daemon` (`moments/` : stockage, lecture bornée, service de trace, repli hooks, diffusion ; `progress/` : outil `ticket_progress` par la route MCP des runs, vérification des fichiers ; rappels par les hooks ; destinataires ; faux `claude` qui écrit une vraie transcription) → `sdk` (`AgentMention`, `HoverCard`, `Popover`, `sdk.runs.peek`, `sdk.openRun`, `statusCardClass`) → `ui` (barre, volet, fil, onglet Activité, mention, volet latéral, page `#/runs/:id`) et composants (`kanban`, `tickets`, `questions`, `graph`) → intégration, E2E, Penpot, jalon.

**Tech Stack:** TypeScript strict, Zod, Bun (`bun:sqlite`, seconde connexion sur `runs.db`), React 19 + shadcn/ui (`radix-ui` déjà présent : `HoverCard`, `Popover`), fast-check, Playwright ; **aucune dépendance nouvelle**.

**Spec:** conception **§26.1 à §26.10** (autorité ; amende §7, §8, §22.1, §23.12 et la spec agents §3, §4, §8, §18) ; passation `docs/superpowers/rapports/2026-10-09-passation-phase-20.md` (choix d'Adam, couleurs du graphe, écarts des maquettes) ; CLAUDE.md. Spec validée par Adam le 2026-10-10 sans modification. **Hors périmètre** : §26.11 (retrait itch et serpent) et §26.12 (dialogue en deux volets), livrés par le correctif `0.19.0-alpha.2` (`fix/composants-alpha2`) avant le rebase de `phase/20`.

## Global Constraints

- **Zéro token pour l'état** : un moment, un plan, un compte rendu, un rappel, un destinataire, un état « démarrable » naissent d'un événement déterministe (ligne de transcription lue par le démon, appel d'outil authentifié par le jeton du run, hook, commande, règle pure). Aucun texte d'agent n'est interprété pour changer un état ; les libellés sont une table.
- **Sécurité** : la transcription n'est lue que pour un run du démon, à un chemin accepté (`realpath` sous la racine des transcriptions, nom `<sessionId>.jsonl`), par passes bornées (4 Mio), jamais envoyée ni synchronisée ; les moments restent locaux (`runs.db`), masqués avant écriture ; seuls le plan et le compte rendu entrent dans le CRDT ; `ticket_progress` n'écrit que sur le ticket du run (projet et ticket imposés par le démon, jamais lus dans l'entrée) ; route MCP des runs : bearer du run **vivant**, locale, `Host` vérifié ; les rappels n'ont jamais de pouvoir de refus.
- **Pureté** : `core` sans I/O (analyse, pliage, commandes, consignes, `readProject`) ; `schema` sans dépendance hors `zod` ; le démon ajoute l'I/O (SQLite, fichiers, git, routes).
- **Dogfooding** : `components/{kanban,tickets,questions,graph}` n'utilisent que `@kibo/schema` et `@kibo/sdk` (`AgentMention`, `useAgentMention`, `useEntities`, `sdk.run`, `sdk.openRun`).
- **Budget UI** : entrée ≤ **224,5 kB** gzip (mesure 223,4 au jalon v0.19, moins le retrait d'alpha.2), plafond 230 jamais relevé ; tout ce qui est nouveau est différé et cité par `FORBIDDEN_IN_ENTRY` (`agents/dock/`, `agents/mention/`, `moments/`, `ticket/activity/`, `agents/RunPage`, `fr-moments.ts`, `sdk/src/ui/hover-card`, `sdk/src/agent-mention`) ; l'entrée ne gagne que la barre (résumé, puces d'étape, poignée) et ≈ 0,4 kB de `fr.ts` ; compensation prévue en T7 (décision 24).
- **Tests sans token** : faux `claude` qui écrit une transcription réaliste et appelle `ticket_progress` par le vrai serveur MCP ; fast-check sur le masquage, le pliage, la réduction transitive et les vagues ; intégration contre un démon temporaire ; E2E sombre et clair.
- **Fichiers** : kebab-case, exports nommés, **aucun commentaire**, < 300 lignes (`question.ts` et `rpc.ts` sont près de la limite : nouveaux fichiers `question-recipient.ts`, `visibility-rpc.ts`) ; textes UI en français dans `packages/ui/src/i18n/fr-moments.ts` (différé), `fr.ts` (entrée, barre seulement) et les `fr.ts` des composants.
- Git : branche `feat/p20-t<n>` depuis `phase/20` (rebasée sur `main` après `0.19.0-alpha.2`), worktree `.claude/worktrees/p20-t<n>` ; commits d'une ligne en français, préfixe conventionnel, **< 50 caractères** (`wc -m`), fichiers stagés explicitement, aucune mention d'IA. `bun run check && bun run typecheck && bun test packages components` verts avant chaque commit final ; `bun run budget` pour toute tâche UI.
- Captures `screens/2026-10-<jj>-t<n>/` (ignoré par git), sombre et clair, à la fin de T7, T8, T9, T10, T11, T13 (avec le mock ou le SDK simulé) et T14 (vrai démon et faux `claude`, écrans 183 à 188k).

## Décisions d'exécution

1. **Racine des transcriptions** : `OrchestratorOptions.transcriptRoot: string`, posée par `daemon.ts` à `join(env.CLAUDE_CONFIG_DIR ?? join(home, ".claude"), "projects")` (le CLI range ses transcriptions sous `CLAUDE_CONFIG_DIR`, que `runner.ts` conserve) ; un chemin est accepté si `realpathSync(dirname(path))` commence par `realpathSync(root) + sep` et si `basename(path) === `${run.sessionId}.jsonl`` (`sessionId` courant du run, mis à jour par `spawned`). Les tests posent `transcriptRoot = <home>/fake` et `KIBO_FAKE_CLAUDE_STATE = <home>/fake/projects` (le faux `claude` nomme déjà le fichier par la session).
2. **Une source par run** : `run_traces.source` ∈ `pending` (aucun hook encore), `transcript`, `hooks`. Le premier hook qui porte `transcriptPath` tranche ; une lecture qui échoue ensuite bascule en `hooks` avec un moment `raw { partial: "unreadable" }` ; en source `hooks`, chaque `PostToolUse` devient une action (`actionFromHook`) regroupée dans un moment `actions` par tour (vidé au `Stop`), et `Stop.detail` (dernier message) devient un `message`. Jamais les deux sources à la fois : pas de doublon.
3. **Store des moments** : `openMomentStore(home)` ouvre une seconde connexion sur `runs.db` (mêmes pragmas, `busy_timeout`) : `run_moments` (append-only par triggers, `UNIQUE(run_id, seq)`, index `(run_id, seq)`), `run_traces` (mutable, une ligne par run) et `run_internal_plans` (mutable). Les sauvegardes (`vacuumInto`) couvrent tout.
4. **Passes sérialisées** : `onHook` et `onTurnEnd` enchaînent les passes d'un même run sur une promesse par run (`Map<runId, Promise>`) ; une passe lit au plus `TRANSCRIPT_PASS_MAX_BYTES` (4 Mio) de lignes complètes, plie, écrit, émet `run.moments` ; s'il reste à lire (`more`), la passe suivante s'enchaîne aussitôt. `onTurnEnd` fait la passe finale puis `flushActions` et pose `closed_at`. Un run terminé n'est plus jamais lu.
5. **Pliage** (`core/moments/`) : un moment `message` par bloc `text` d'assistant, `reasoning` par bloc `thinking`, `actions` = tous les `tool_use`/`tool_result` entre deux textes (vidés avant chaque `message`/`reasoning` et à la fin du tour) ; les lignes `isSidechain` (sous-agents) apportent leurs outils aux actions mais pas leurs textes ; `maskSecrets` est appliqué **dans le pliage** à tout texte (message, raisonnement, label, cible, détail, raw) : aucun chemin d'écriture ne peut l'oublier ; l'horodatage vient de `timestamp` quand il est lisible, sinon de `now()`.
6. **Lien étape ↔ moments** : `run_traces.doing_step` est posé par le service de progression à chaque plan reçu (`doingStep(plan)?.id ?? null`) ; tout moment écrit ensuite porte ce `stepId`. Une étape renvoie à ses moments par `moments.filter(m => m.stepId === step.id)` (UI). Déterministe : l'appel d'outil précède son `PostToolUse` et la passe de lecture.
7. **`ticket_progress` par la route MCP des runs** : les runs de ticket reçoivent `KIBO_MCP_URL = <base>/agent-mcp/<runId>` et `KIBO_MCP_TOOLS=ticket` (`LaunchInput.mcpTools: "project" | "ticket" | null`) ; `kibo-hook mcp` liste `ticket_progress` seulement avec `KIBO_MCP_TOOLS=ticket` (les dix outils de projet avec `project`) et relaie `tools/call` par `callDaemonTool` ; la route dispatche sur `run.kind` : `project` ⇒ outils de projet, `ticket` ⇒ `ticket_progress` seul, sinon `403`. L'agent reçoit « Plan enregistré. » / « Compte rendu enregistré. » **après** l'écriture dans le CRDT (réponse honnête), ou le détail d'erreur Zod en `isError`. Le `PostToolUse mcp__kibo__ticket_progress` reste un hook ordinaire (action « A déclaré son plan (5 étapes) »).
8. **Compte rendu et fichiers** : `setTicketProgress { ticketId, runId, at, plan?, report?, check? }` : `plan` remplace le plan entier ; `report` remplace le compte rendu du même `runId` ou l'ajoute (20 au plus, les plus anciens sortent) ; `check` pose `undeclared`/`unchanged` sur le compte rendu de ce run. `base_head` = `git rev-parse HEAD` dans `cwd` au premier `spawned` du run (trace) ; à **chaque fin de tour** (`onTurnEnd`, après la sortie du processus, qui suit toujours le hook `Stop`), si le run a un compte rendu : `changedFiles(git, cwd, baseHead)` = `git diff --name-only <base>` ∪ `git ls-files --others --exclude-standard` (chemins relatifs au dépôt) ; `checkFiles(declared, changed)` compare après normalisation (`./` retiré, séparateurs `/`) ; hors dépôt ⇒ `check: null` (« fichiers non vérifiés »).
9. **Rappels** en mémoire (`Map<runId, { plan: boolean; report: boolean }>`, perdus au redémarrage comme le run lui-même) ; `withReminders(sink, deps)` décore le puits : `PreToolUse` d'un outil de `MODIFYING_TOOLS` sur un run de ticket sans plan ⇒ si le puits sous-jacent n'a pas refusé, réponse `{ kind: "permission", decision: "allow", reason: "", additionalContext: PLAN_REMINDER }` ; `Stop` sans compte rendu, `stopHookActive` faux ⇒ `{ kind: "stop", reason: REPORT_REMINDER }` ; chacun une fois.
