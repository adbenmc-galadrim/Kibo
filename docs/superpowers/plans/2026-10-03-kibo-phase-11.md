# Kibo · Phase 11 : suivis techniques après v1.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** fermer les quatre suivis techniques laissés ouverts par le jalon v1.2 (rapport du 3 octobre, section « Écarts et points ouverts », et passation de la phase 10, section « Suivis techniques sans décision ») : un libellé juste dans les files d'attente quand un simple message relance un run, une durée de run qui ne compte plus le temps d'arrêt du démon, un test d'aperçu qui ne dépend plus de l'ordre des minuteries, et un contenu de composant qui occupe la hauteur de son format dans l'aperçu Demi-page. Aucune décision produit, aucun token consommé, budget de chargement initial jamais relevé.

**Architecture:** quatre tâches indépendantes, sans fichier partagé. La machine à états des runs (`packages/core`) garde la question de l'agent jusqu'au début du tour suivant, ce qui permet à la file de distinguer une réponse d'un message sans lire le journal ; le registre des runs (`packages/daemon`) date l'événement `failed` d'un run interrompu du dernier événement de son journal au lieu de l'instant du redémarrage ; le test du squelette de l'aperçu crée sa promesse avant le montage et attend la demande de construction avant de la libérer ; le skill de l'agent, son exemple, le gabarit de `kibo component new` et les fixtures du faux `claude` donnent au corps de la carte `flex min-h-0 flex-1 flex-col`, et le parcours E2E `creations` mesure le résultat dans le cadre Demi-page.

**Tech Stack:** Bun 1.4.2, TypeScript 5.9 strict, Zod 3.25.76, React 19 + shadcn/ui, Vite 7.3.5, happy-dom + Testing Library, Playwright (Chromium), SQLite (`bun:sqlite`). Aucune dépendance nouvelle.

**Spec:** `docs/superpowers/specs/2026-09-26-kibo-agents.md` **§14.4** (point « Files d'attente », écrit pour ce plan : réponse ou message, `question` gardée jusqu'au `spawned`), **§14.6** (nouveau : run interrompu daté du dernier événement), §14.2 (durée) ; `docs/superpowers/specs/2026-09-26-kibo-composants.md` **§17 point 2** (« Hauteur du contenu », écrit pour ce plan), §17 point 5 (aperçu d'un brouillon). Sources des suivis : `docs/superpowers/rapports/2026-10-03-jalon-v1.2.md`, `docs/superpowers/rapports/2026-10-03-passation-phase-10.md`.

## Review Focus

1. **Message pendant un tour qui finit par une question** (T1) : le run passe `waiting_input` → `requeued` avec sa `question` ; la file affiche « réponse reçue · reprise de la session » (le message vaut réponse, spec §14.4) ; au `spawned` suivant, `question` et `pendingAnswer` sont `null`, et une sortie propre donne `done`, pas `waiting_input`.
2. **Run `starting` interrompu** (T2) : admis mais jamais `spawned` ⇒ `failed` daté de l'admission, `activeMs: 0`, `turnStartedAt: null`.
3. **Journal écrit par un démon antérieur** (T2) : un `failed` `INTERRUPTED` daté du redémarrage se relit tel quel, la durée affichée ne change pas, le run n'est pas dans `interrupted()` et aucun second `failed` n'est ajouté.
4. **Run `queued` avec message au redémarrage** (T2, spec §14.4) : reste `queued`, garde `pendingAnswer` et son rang, n'est pas dans `interrupted()`.
5. **Exemple, gabarit et fixtures dans tous les formats** (T4) : l'exemple du skill passe toujours la validation complète (`prompts-example.int.test.ts`, conformité dans les cinq formats, largeurs fixes), le gabarit de `kibo component new` compile, et la fixture révisée s'affiche encore en Moyen après la révision (E2E).
6. **Squelette retiré** (T3) : une fois le cadre affiché, plus aucun `role="status"` dans le dialogue.

## Décisions

Les décisions de comportement sont écrites en spec agents §14.4 et §14.6 et spec composants §17 point 2 ; le plan ne les répète pas. Décisions d'exécution :

1. **`question` gardée plutôt qu'un champ nouveau.** Ajouter un champ dérivé à `RunView` aurait touché huit fichiers de fixtures (liste de la phase 10, T7) pour porter une information que la vue a déjà : la question à laquelle le run va répondre. `resumeHead` cesse de l'effacer ; `spawned` l'efface (le tour qui démarre la consomme). Aucun lecteur hors `waiting_input` n'existe (vérifié ci-dessus) ; `applyExit` ne voit `question` que pendant un tour, après `spawned`.
2. **Date de clôture = dernier événement du journal**, pas `lastActivity.at` (absent pour un run sans hook) ni `turnStartedAt` (perdrait le travail observé). `replay` renvoie `lastAt: Map<string, number>` ; `now()` ne sert plus qu'à `create` et `apply`.
3. **Le test du squelette crée sa promesse avant le montage** (`deferred()`), attend explicitement l'appel `previewComponentDraft` avant de libérer, et vérifie qu'à ce moment le squelette est toujours là : le test énonce la séquence au lieu de la supposer. Aucun changement de `DraftPreviewFrame`.
4. **Hauteur du corps par les classes du composant**, pas par `card.tsx` : `CardContent` est une primitive shadcn partagée par toute l'interface ; `flex-1 min-h-0` sur toutes les cartes changerait des écrans qui n'ont rien demandé. La règle vit où le composant est écrit : skill, exemple, gabarit, fixtures. Le corps garde l'en-tête fixe ; `overflow-auto` reste sur la racine (règle existante du skill) : le dev ne déplace pas le défilement.
5. **Mesure E2E dans le cadre** : `frame.locator('[data-slot="card"]').evaluate(…)` lit `getBoundingClientRect` dans le document du bac à sable (1196 × 560 px CSS), insensible à `transform: scale` du cadre.
