# Kibo · Phase 32 : écrire depuis la CLI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** la commande `kibo` écrit ce que l'API sait déjà faire (spec **§48**) : `features create`, `tickets create|update|move|link|unlink`, `sprints create|update|assign`, `questions list|add|answer`, toutes par la RPC `command` et `ProjectCommand`, clés résolues côté CLI, acteur humain (§48.1) ; **`kibo plan apply <fichier> [--dry-run]`** applique d'un bloc un fichier YAML ou JSON d'actions `ProposedAction` restreintes (références `new:<n>`), validé en entier avant toute écriture par `validateBatch`, appliqué dans l'ordre avec arrêt à la première erreur et liste de ce qui a été créé, clés futures prédites en simulation (§48.2) ; `plan export --md` et `tickets list --feature/--label/--fields` (§48.3) ; `kibo rpc '<json>'` (§48.4) ; `docs/cli.md` avec la section API (§48.5) ; erreurs du noyau et de la CLI qui disent quoi faire (§48.6). Pas d'interface, pas de maquette, pas de Penpot.

**Architecture:** rien n'est dupliqué : la CLI envoie des `ProjectCommand` existantes ; le plan réutilise le schéma des lots (`ProposedAction`, `NewRef`), la validation pure de `packages/core/src/project-agent/validate.ts` (contexte allégé `planContext`) et l'exécution des lots, dont la partie « une action ⇒ ses commandes » sort de `apply-batch.ts` vers **`apply-actions.ts`** (partagée par les lots et le plan). Deux RPC locales `previewPlan`/`applyPlan` servies par un **service de plan** (`packages/daemon/src/plan/`) construit dans `bootstrap.ts` sur le même port de données que l'agent de projet, enregistré dans les extensions du démon. Le schéma gagne `createTicket.feature` sur `ProposedAction`, `plan.ts` (types et sous-ensemble d'actions) et `plan-rpc.ts`. Dans la CLI : `args.ts` apprend les drapeaux répétés (`--option`), un lecteur `@fichier|@-`, une table de traduction des erreurs, un acteur ; un module par portée (`features.ts`, `tickets-write.ts`, `tickets-link.ts`, `sprints.ts`, `questions.ts`, `plan-export.ts`, `plan-apply.ts`, `rpc.ts`) avec ses textes dans un `fr-<portée>.ts`.

**Tech Stack:** Bun 1.4.2 (`Bun.YAML.parse`), TypeScript strict, Zod 3.25, fast-check (`predictKeys`), Biome, démon Bun + SQLite pour les tests d'intégration (`startDaemon`, `KIBO_HOME` temporaire), harnais `fakes.test-helper.ts`.

**Spec:** `docs/superpowers/specs/2026-09-25-kibo-design.md` **§48** (amende §34, §4, §24). Décisions prises dans ce plan : « Décisions d'exécution » ci-dessous, à reporter en §48.7 au jalon si elles s'écartent.

## Global Constraints

- **Spec §48 fait foi** ; une décision absente est tranchée dans « Décisions d'exécution » et reportée en §48.7 au jalon.
- **Aucune écriture directe** : la CLI n'envoie que `command` (et `previewPlan`/`applyPlan`, `declareTicketRef` déjà là) ; le service de plan n'écrit que par `data.runCommand`.
- **Pas de duplication** : une seule fonction « action ⇒ commandes » (`commandsFor`, core), une seule exécution (`runAction`, `apply-actions.ts`), une seule validation (`validateBatch`) ; le plan CLI **n'est pas** un lot : aucun `Batch`, aucun `runId`, rien dans la conversation.
- **Dépendances entre paquets** (CLAUDE.md) : `cli` dépend de `schema`, `devkit`, `trust` ; le démon reste `devDependency` des tests ; `core` sans I/O ; aucune dépendance nouvelle (YAML par `Bun.YAML`).
- **Code** : TypeScript strict, aucun commentaire, pas de `any` ni de `as` non justifié, exports nommés, kebab-case, ~300 lignes par fichier (`tickets-test-kit.ts` et `fr.ts` sont à découper plutôt qu'à gonfler) ; identifiants et `detail` d'erreur en anglais ; **textes de la CLI en français** dans `packages/cli/src/fr*.ts` ; messages de `validateBatch` en français (existant).
- **Dépôt public** : données fictives « Silo » seulement dans les tests, la doc et l'exemple de plan ; `FORBIDDEN_TERMS_SCOPE=<zone> bun test scripts/forbidden-terms` avant chaque commit ; le jeton d'appairage n'apparaît jamais dans une sortie.
- **Tests sans token** : TDD ; faux démon de la CLI pour les commandes, harnais du démon pour le service de plan, un vrai démon temporaire pour l'intégration (port `0`, `KIBO_HOME` dans `mkdtemp`, fermé en `afterAll`).
- Git : branche `feat/p32-t<n>` depuis `phase/32`, worktree `.claude/worktrees/p32-t<n>` ; commits d'une ligne en français, préfixe conventionnel, **< 50 caractères**, un seul `-m`, fichiers stagés explicitement, **aucune mention d'IA**. `bun run check && bun run typecheck && bun test <zone>` verts avant chaque commit final.
