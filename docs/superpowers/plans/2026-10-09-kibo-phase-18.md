# Kibo · Phase 18 : Agent de projet Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** un agent de gestion de projet par projet, dans un panneau latéral (⌘J), porté par un run de projet (`kind: "project"`) dont la session Claude est reprise de message en message. Il lit le projet par le serveur MCP `kibo` étendu (route authentifiée `POST /agent-mcp/<runId>`), garde le contexte (instantané au premier tour, digest « depuis ton dernier tour » par différence d'empreintes, note mémoire `agent-de-projet/memoire.md`) et **propose des lots d'actions** (tickets, agents, questions, notes) qu'un éditeur valide d'un clic ; les actions s'appliquent par les commandes existantes, avec détection des cibles périmées. « Nouvel agent de projet » repart d'une session neuve ; les anciennes restent lisibles.

**Architecture:** `schema` (actions, lot, RPC, outils MCP, `RunKind`) → `core` (validation du lot, plan d'application et périmées, références `new:`, empreinte et digest, instantané, consignes du run : pur, fast-check) → `daemon` (migration `runs.kind`, run de projet reconstructible dans l'orchestrateur, `project_agent_sessions` et `project_agent_batches` dans `runs.db`, service de l'agent de projet, route MCP, exécuteur de lots, profil système `project-agent`) → `kibo-hook mcp` (vrais outils qui interrogent le démon) → `ui` (panneau chargé à la demande, carte de lot, badge, ⌘J) → E2E et Penpot.

**Tech Stack:** TypeScript strict, Zod, Loro (lecture seule ici), Bun SQLite, React 19 + shadcn/ui, Playwright, fast-check, faux `claude` (`fake-claude.ts`) étendu d'une étape `mcp`.

**Spec:** conception §24 (autorité), agents §3, §4, §13, §14.4, §18 ; CLAUDE.md. Les décisions prises ici parce que §24 les laissait ouvertes sont listées dans « Décisions d'exécution » ; une seule correction de §24 est appliquée, avec ce plan (§ « Amendement de la spec »).

## Global Constraints

- **Zéro token pour l'état** : l'agent n'écrit jamais dans Kibo ; `propose_batch` enregistre un lot `pending`, rien d'autre. Le démon capture lui-même l'état attendu des cibles. Aucune interprétation du texte de l'agent.
- **Tout tour passe par la file** : un run de projet est un run comme les autres (créneau, `maxParallel`, seuils), admis en tête (`headRank`) ; une seule session ouverte par projet, donc un seul tour à la fois par projet.
- **Sécurité** : route `/agent-mcp/<runId>` locale, bearer = jeton du run **vivant**, run de kind `project` ; le projet vient du run, jamais de l'entrée ; `permissions.deny` fixe + garde `PreToolUse` déterministe ; jeton jamais sur la ligne de commande (`--mcp-config` sans `env`).
- **Pureté** : `core` sans I/O (validation, plan, empreinte, digest, instantané, consignes) ; le démon n'ajoute que l'I/O (SQLite, notes, commandes, orchestrateur).
- **Budget UI** : entrée ≤ **226,4 kB** gzip (valeur mesurée aujourd'hui), plafond 230 jamais relevé ; panneau, i18n `fr-project-agent.ts`, carte de lot et bouton en chunk différé (`FORBIDDEN_IN_ENTRY`).
- **Tests sans token** : faux `claude` avec étape `mcp` réelle (il lance `kibo-hook mcp` depuis `--mcp-config`), scénarios `project-agent-*.json`, fast-check sur la validation et l'application, intégration contre un démon temporaire, E2E sombre et clair.
- **Fichiers** : kebab-case, exports nommés, aucun commentaire, < 300 lignes (découper `project-agent/` en modules), textes UI dans `packages/ui/src/i18n/fr-project-agent.ts` (différé) et une entrée `fr.header.projectAgent` (entrée).
- Git : branche `feat/p18-t<n>` depuis `phase/18` (créée depuis `phase/17` + spec `63d2e41c`), worktree `.claude/worktrees/p18-t<n>` ; commits d'une ligne en français, préfixe conventionnel, **< 50 caractères**, fichiers stagés explicitement, aucune mention d'IA. `bun run check && bun run typecheck && bun test packages components` verts avant chaque commit final ; `bun run budget` pour toute tâche UI.

## Décisions d'exécution

1. **Un run par session** : une session de l'agent de projet **est** un run `kind: "project"` ; chaque message est un tour (`answered` → `queued` en tête ou `pendingAnswer`). « Nouvel agent de projet » ferme la session (`closed_at`) et le message suivant crée un **nouveau run** (nouveau `sessionId`). `project_agent_sessions.run_id` est la clé de la session ; les anciennes sessions sont les anciens runs du projet, lisibles par `getRunLog`. `isLatestOfTicket` (qui compare `ticketId: null` et `projectId`) rend l'ancien run non reprenable sans code nouveau.
2. **`brief` vide, message par `answered`** : un run de projet naît avec `brief: ""` et reçoit aussitôt `answered { text }` (même méthode `startProjectRun`) : le prompt de **chaque** tour est `pendingAnswer` (messages concaténés par la machine), précédé par le démon de l'instantané (tour 1) ou du digest (tours suivants). Un message envoyé pendant que le premier tour est en file s'ajoute au premier message au lieu de le remplacer ; « Réessayer » renvoie le dernier message (le `failed` a effacé `pendingAnswer`) et la conversation montre une ligne « Nouvelle tentative ».
3. **`RunKind = "ticket" | "project"`** (§24.6) : `kind` requis sur `RunRecord` ; les runs historiques et les runs `submit()` (brouillons de composant) restent `"ticket"` avec `ticketId: null`, inchangés. La propagation mécanique de `kind: "ticket"` dans les littéraux de test est faite en **T1** pour que la vague 2 parte d'un typecheck vert.
4. **Prompt et cwd fournis par un port** : `OrchestratorOptions.projectTurns: ProjectTurnPort` ; le lanceur (`run-launch.ts`) appelle `prepare(run, runDir)` pour un run de projet au lieu de `prepareWorkspace` : `cwd` = dossier du projet s'il existe (`existsSync`), sinon `<runDir>/workspace` créé ; `CLAUDE.md` écrit par `writeRunContext`. Le service de l'agent de projet implémente le port ; l'orchestrateur ne connaît ni lot ni session.
5. **Session d'un run de projet** : `decideProjectSession(run, transcriptExists, newId)` (pur, `session-decision.ts`) : tour 1 ⇒ `fresh/no_previous` avec `run.sessionId` ; tours suivants ⇒ `resumed` (`from: run.id`) si le transcript existe, sinon `fresh/transcript_missing` avec un UUID neuf porté par `spawned.sessionId`. Journal `session` à chaque tour (accepté en `starting`).
6. **Allow/deny et garde** : `claudeSettings(hook, allow, deny = [])` écrit `permissions.deny` quand la liste n'est pas vide ; pour un run de projet le lanceur passe `allow = [...PROJECT_AGENT_MCP_TOOLS, ...PROJECT_AGENT_READ_TOOLS, ...profile.allow]`, `deny = PROJECT_AGENT_DENY` ; `projectRunGuard(run)` (comme `demoRunGuard`) refuse au `PreToolUse` tout outil de `PROJECT_AGENT_DENY` : ceinture et bretelles, déterministe.
7. **URL MCP par l'environnement** : `LaunchInput.mcpUrl: string | null` ⇒ variable `KIBO_MCP_URL = <baseUrl>/agent-mcp/<runId>` dans l'env du processus `claude` ; `kibo-hook mcp` la lit avec `KIBO_RUN_TOKEN` (hérités par le serveur stdio). Rien sur la ligne de commande ; `cleanEnv` retire aussi `KIBO_MCP_URL` de l'env parent.
8. **Réponses d'outil en texte** : la route rend `{ ok: true, text }` ou `{ ok: false, error }` ; `kibo-hook mcp` relaie `content: [{ type: "text", text }]` et `isError` sur erreur. Les outils de lecture rendent du **JSON compact** (`JSON.stringify` sans espaces) ; `propose_batch` rend une phrase (« Lot 3 enregistré, en attente de validation de adam. ») ou les erreurs action par action (une ligne `#<id> <type> : <message>`).
9. **Pagination par décalage** : `cursor` = décalage décimal en chaîne, 50 éléments par page (`PAGE_SIZE`), `nextCursor: null` à la fin.
10. **Empreinte à l'ouverture du tour** : `prepare` calcule l'empreinte **au moment de composer le prompt** et l'enregistre sur la session ; le digest du tour suivant = `diff(empreinte enregistrée, projet actuel)`, ce qui inclut les lots appliqués après la fin du tour. Les empreintes de notes sont des sha256 calculés par le démon (`noteHashOf` déplacé dans `notes/note-hash.ts`) ; `core` ne hache rien.
11. **Deux tables, un seul fichier** : `openProjectAgentStore(home)` ouvre une **seconde connexion** sur `runs.db` (mêmes pragmas, `busy_timeout`) : `project_agent_sessions` (mutable : `closed_at`, `fingerprint`, `last_turn_at`), `project_agent_batches` (append-only, triggers) et `project_agent_batch_events` (append-only). Le statut d'un lot est le repli de ses événements (`foldBatch`, pur, schéma). `vacuumInto` des sauvegardes couvre tout.
12. **Application dans l'ordre, sans transaction globale** : un lot s'applique action par action (chaque commande est elle-même transactionnelle) ; une action en échec n'arrête pas les autres (§24.4). L'état « actuel » pour la détection des périmées est lu **une fois** au début de l'application (les actions du même lot ne se périment pas entre elles : la validation refuse déjà deux actions sur le même champ de la même cible).
13. **Acteur humain** : l'exécuteur passe `by: { kind: "human", ref: viewer }` et `docs.run(..., USER_COMMAND)` ; l'intercepteur existant réécrit de toute façon l'acteur des questions. `assignAgent` ⇒ `orchestrator.assign` ; `deliverAnswers` ⇒ `service.deliverAnswers` ; `cancelRun` ⇒ `orchestrator.cancel` ; notes ⇒ `createNoteFile`/`writeNoteFile` via le port (`expectedMtime` lu juste avant, l'empreinte ayant déjà été vérifiée).
14. **Refus = un message** : `decideBatch reject` avec commentaire ⇒ `send(projectId, "Lot n refusé : <commentaire>")` (un tour) ; sans commentaire ⇒ aucun tour, la carte dit « Refusé ». Un lot `pending` antérieur du projet passe `superseded` à l'enregistrement d'un nouveau ; « Nouvel agent » passe le `pending` courant à `abandoned`.
15. **Badge sans RPC supplémentaire** : `AgentsState.projectAgents: ProjectAgentSummary[]` (run courant et `pendingBatchId` par projet) calculé dans `agents-rpc.ts` depuis un fournisseur attaché (`Service.attachProjectAgent`) ; le bouton (chunk différé, `fallback: "children"`) lit `useAgentsState()` déjà chargé ; le panneau recharge `getProjectAgent` sur le sujet `agents` (émis à chaque changement de run **et** de lot : pas de nouveau `Topic`).
16. **Libellé des runs de projet** : `ticketTitle = "Agent de projet · <nom du projet>"` posé par le démon à la création (comme « Composant <titre> ») : pages Agents, Files d'attente, cloche et notifications l'affichent sans changement ; renommer le projet ne met pas à jour les runs passés (écart accepté).
17. **Panneau = `Sheet` non modal + état local** : `open` et `width` dans `usePref` (`kibo.projectAgent.open`, `kibo.projectAgent.width`), **pas** dans `DialogsState` (`anyDialogOpen` fausserait `useKeepOnEdit`) ; poignée de redimensionnement sur le motif de `ResizeHandles.tsx` (pointeur + Maj+flèches), bornée 360 à 720 px ; le panneau suit `project` du `Workspace` et se ferme (sans oublier sa largeur) quand aucun projet n'est affiché.
18. **Markdown sans dépendance** : la conversation rend le texte de l'agent avec `renderContext` extrait dans `packages/sdk/src/markdown-lite.tsx` (déplacé depuis `components/questions/src/render-context.ts`, réexporté là : un composant n'importe pas l'UI) et un linkifieur de clés (`/\b[A-Z]{2,6}-\d+\b/`) qui ouvre la fiche (`host.openTicket`) ; `markdown-it` reste interdit.
19. **Vagues** : T1 seule ; T2, T3, T4, T5 en parallèle, fichiers disjoints (T2 : `packages/core/src/project-agent/**` ; T3 : `daemon/agents/{run-store,orchestrator,orchestrator-types,run-launch,runner,hook-sink,session-decision,project-guard}.ts`, `core/{run-machine,run-resume,agent-profiles}.ts`, `schema/agent.ts` (id système) ; T4 : `daemon/agents/{ask-mcp,kibo-hook,hook-payload,fake-claude,fake-claude-scenario,fake-claude-mcp}.ts`, scénarios ; T5 : `packages/ui/**`, `schema/protocol.ts`, `menu.rs`) ; T6 et T7 en parallèle dans `daemon/src/project-agent/` (T6 : `store`, `service`, `rpc`, `mcp-route`, `server.ts`, `service.ts`, `agents-rpc.ts`, `daemon.ts` ; T7 : `data-port`, `tools`, `apply-batch`, `notes/note-hash.ts`) ; T8 intégration, scénarios et E2E ; T9 Penpot et T10 jalon.
