# Kibo · 0.29.0-alpha.3 : réveil automatique de l'agent de projet sur une réponse Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** livrer la **0.29.0-alpha.3** (spec **§43**, décision d'Adam du 2026-10-19 sur maquette ASCII) : quand une réponse à une question est enregistrée, l'agent de projet se réveille comme pour un blocage, la lit aussitôt et propose un lot si besoin ; un tour par réponse, les réponses arrivées ensemble regroupées ; dans le panneau Suivi, une ligne « Q16 répondue : « 5 Go » », le texte de l'agent et la carte du lot « Valider / Refuser ». Cela remplace la décision « aucun réveil » de §42.

**Architecture:** aucun second planificateur. La commande `answerQuestion` / `updateAnswer` d'origine `user` et d'acteur `human` (hook `afterQuestionCommands`, déjà appelé après chaque commande de question) met la question dans une **file d'attente du réveil** (table SQLite du store des signaux) et demande un réveil au **planificateur existant** (`createWakeupScheduler`, `planWakeup`, fenêtre 10 min, `due_at` persistant). À l'échéance, le démon relit les questions de la file dans l'instantané courant, ne cite que celles encore répondues (réponse du moment), vide la file et envoie **un seul message** « Réveil automatique : … » par le chemin de `ProjectAgentService.send` (session ouverte ⇒ tour suivant ; sinon nouvelle session), donc par la file d'attente des agents. Le message garde `WAKEUP_PREFIX` : l'interface le reconnaît déjà comme un événement ; il gagne une ligne par réponse (`- Qn répondue : « … »`) que l'interface relit pour afficher une ligne d'événement par réponse, dans la Conversation comme dans le Suivi, où elle ouvre le dernier échange comme une question d'Adam.

**Tech Stack:** Bun, TypeScript strict, Zod, Loro, SQLite (`bun:sqlite`), fast-check, Biome, React 19 + shadcn/ui (`@kibo/sdk/ui`), `lucide-react` (`AlarmClock`), Playwright 1.55, faux `claude` (`packages/daemon/src/agents/fake-claude.ts`, scénarios JSON), Penpot auto-hébergé en **Chromium headless** (Playwright, CDP, plugin MCP, `receiver.py` 8787), `pypdf` (venv hors dépôt), `xz`.

**Spec:** `docs/superpowers/specs/2026-09-25-kibo-design.md` **§43** (s'appuie sur §24.6, §27.4, §27.7, §38.1, §42 ; amende §27.4, §27.7 et §42 premier point).

## Review Focus

1. **Pas de boucle ni de réveil parasite** (T2) : une réponse appliquée par un lot de l'agent de projet (origine `agent`), une réponse importée (`by.kind = "import"`), une commande `kibo` ou `sync`, un `reopenQuestion`, un `archiveQuestion` n'appellent jamais `wake` ; cinquante réponses d'un import ne produisent aucun réveil ; cinquante réponses d'un utilisateur en produisent **deux au plus** (un immédiat, un à +10 min), vérifié par la propriété fast-check existante étendue aux réponses.
2. **La réponse citée est celle du moment** (T2) : réponse modifiée avant l'échéance ⇒ la ligne porte la nouvelle réponse, une seule ligne ; réponse retirée, question archivée ou supprimée ⇒ aucune ligne, et sans signal déclencheur **rien n'est envoyé**, `dueAt` effacé, file vidée ; projet non modifiable ⇒ rien n'est envoyé, file vidée.
3. **Le message reste lisible par l'interface** (T1, T3) : `wakeupCount` rend toujours le nombre de signaux sur un message mixte et `null` sur un message de réponses seules ; `wakeupAnswers` rend les couples `{ label, quote }` même quand la réponse contient « », des parenthèses ou un « - » en tête ; un message de signaux seuls est **identique octet pour octet** à celui d'avant (test de non-régression sur la chaîne complète).
4. **Suivi** (T3) : un réveil ouvre le dernier échange (résumé épinglé, ligne de réveil, texte de l'agent, lot) ; sans message d'Adam ni réveil, rien ne change ; `lastUserMessage` (« Réessayer ») ignore toujours un réveil ; le lot qui suit porte « après réveil » ; une session dont le premier message est un réveil affiche la ligne puis le texte en résumé.
5. **Rejeu et file des agents** (T2) : une échéance laissée par le démon précédent avec des réponses en file est rejouée au démarrage et cite ces réponses ; un réveil pendant un tour en cours est joint au tour suivant sans second run (`turns` de la vue du run passe de 1 à 2, un seul `runId`).

## Décisions d'exécution

1. **Déclencheur** : dans `afterQuestionCommands`, pour chaque `CommandEvent` dont `command.method ∈ { answerQuestion, updateAnswer }`, `meta.origin === "user"` et `command.by.kind === "human"` ⇒ `deps.wake(projectId, questionId)` (`wake: AnswerWake | null`, `AnswerWake = (projectId: string, questionId: string) => void`). Une commande refusée n'atteint pas `published` : rien à filtrer. Un pair synchronisé n'émet pas de commande ici : rien à filtrer non plus (consigné en §43).
2. **File d'attente du réveil** : table `project_agent_wakeup_answers (project_id TEXT NOT NULL, question_id TEXT NOT NULL, queued_at INTEGER NOT NULL, PRIMARY KEY (project_id, question_id))` dans `SCHEMA` du store des signaux (pas append-only : on la vide). `SignalStore` gagne `queueAnswer(projectId, questionId, at)` (upsert : `queued_at` conservé), `queuedAnswers(projectId): string[]` (ordre `queued_at, question_id`), `dropAnswers(projectId): void`. `WakeupStore` = `Pick<SignalStore, "wakeup" | "saveWakeup" | "due" | "open" | "queueAnswer" | "queuedAnswers" | "dropAnswers">`.
3. **Planificateur** : `WakeupDeps` gagne `answered(projectId: string, questionIds: readonly string[]): AnsweredLine[]` ; `WakeupScheduler` gagne `requestAnswer(projectId, questionId): WakeReply` = `store.queueAnswer(projectId, questionId, now())` puis le même plan que `request` (fonction privée `plan(projectId)` partagée : `planWakeup` ⇒ `fire` / `schedule` / `already`). `wake(projectId)` : `triggers` = signaux ouverts de `WAKE_KINDS` ; `answers = deps.answered(projectId, store.queuedAnswers(projectId))` ; `store.dropAnswers(projectId)` **toujours** ; si `!writable` ou (`triggers` et `answers` vides) ⇒ `saveWakeup({ ...current, dueAt: null })`, rien d'envoyé ; sinon `send(projectId, wakeupMessage({ signals: triggers, answers }))` et `saveWakeup({ lastAt: now, dueAt: null })`. `request(projectId, kind)` inchangé pour l'appelant.
4. **Résolution des réponses** (`bootstrap.ts`) : `answered(projectId, ids)` lit `readProject(docs.project(projectId), docs.today()).questions`, garde les `q` trouvées avec `isAnswered(q)` et rend `{ label: questionLabel(q), quote: answerQuote(q.answer) }` dans l'ordre des `ids`. `startSignals` rend en plus `wakeOnAnswer(projectId, questionId): void` (= `scheduler.requestAnswer`, résultat ignoré, exceptions journalisées par `guarded` du planificateur).
5. **Citation** (`packages/schema/src/wakeup-message.ts`) : `ANSWER_QUOTE_MAX = 120` ; `answerQuote(answer: QuestionAnswer): string` = option (`option` / `confirm`) ou `text`, blancs repliés (`/\s+/g` ⇒ espace, `trim`), vide ⇒ « (vide) », au-delà de 120 points de code ⇒ 119 + « … ». `AnsweredLine = { label: string; quote: string }` ; `answeredLine(l)` = `` `- ${label} répondue : « ${quote} »` `` ; `wakeupAnswers(text): AnsweredLine[]` = lignes de `text` (après le préfixe, `text.split("\n")`) qui vérifient `^- (Q\d+|Q\?) répondue : « (.*) »$` (gourmand, ancré : une réponse contenant « » ou des parenthèses est relue telle quelle) ; `[]` si `!isWakeupMessage(text)`. Export par `packages/schema/src/index.ts`.
6. **Message** (`core/src/signals/messages.ts`) : `wakeupMessage(input: { signals: readonly Pick<Signal, "kind">[]; answers: readonly AnsweredLine[] })`. Signaux seuls : chaîne **inchangée**. Réponses seules : `${WAKEUP_PREFIX}${counted(n, "réponse à lire", "réponses à lire")}.\n${lines}\n${ANSWER_RULE}` avec `ANSWER_RULE` = « Lis chaque réponse (`list_questions`, `get_ticket`) et propose un lot seulement si elle appelle une action : lever un blocage (`setStatus`), ajuster ou reprendre une étape (`updateTicket`, `setHold`), prévenir le client (`createQuestion` à son destinataire) ; sinon dis en une phrase ce que tu en retiens, sans lot. ». Mixte : `${WAKEUP_PREFIX}${counted(signaux)} à traiter (${byKind}) et ${counted(réponses)}.\n${lines}\n${SIGNAL_RULE} ${ANSWER_RULE}` (`SIGNAL_RULE` = la consigne actuelle « Lis « Signaux à traiter » et propose un lot : … »). `wakeupCount` relit le nombre de signaux dans les deux formes qui en ont.
7. **Prompt système** (`prompt.ts`, `questionLines()`, cinquième règle) : « - Réveillé par une réponse (message « Réveil automatique : n réponse(s) à lire »), lis-la dans `list_questions` et propose un lot seulement si elle appelle une action (débloquer, ajuster ou reprendre une étape, prévenir le client) ; sinon dis en une phrase ce que tu en retiens, sans lot. »
