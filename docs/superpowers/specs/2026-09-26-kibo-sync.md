# Kibo — Spec G : sync et multi-utilisateur temps réel (phase 7)

- **Date** : 2026-09-26 · **Phase** : 7 (v1.0) · **Statut** : à valider
- **Parent** : `2026-09-25-kibo-design.md` §2.1, §5, §10, §12 · **Maquettes** : aucune pour la sync (voir §11)
- **Suppose livrés** : phases 1 à 6. `SecretStore` (phase 5) sert à garder les clés privées.

## 1. Objectif

Partager un projet entre plusieurs personnes en temps réel, sans réécriture : le doc Loro du projet (déjà l'unité prévue de sync et de permissions) est relayé par un serveur Bun auto-hébergé. Kibo reste local-first : tout fonctionne hors ligne, la sync rattrape au retour.

## 2. Périmètre

- `packages/sync-server` : serveur de sync Loro (Bun, SQLite), binaire `kibo-sync` avec CLI d'administration.
- Client de sync dans le démon ; comptes, appareils, invitations ; rôles par projet.
- Temps réel (mises à jour Loro) et présence (état éphémère).
- **Décision §12 : clés de ticket allouées par le serveur**, clé provisoire locale.
- Chiffrement en transit ; opt-in explicite du partage ; opt-in explicite de l'accès distant au démon ; persistance des sessions d'appairage (décision §12).
- Ce qui ne se synchronise pas, et pourquoi (§3.4).

## 3. Modèle de données

### 3.1 Serveur (SQLite, `0600`)

```
users(id, name, createdAt, disabledAt)
devices(id, userId, publicKey /* Ed25519 SPKI base64 */, name, createdAt, lastSeenAt, revokedAt)
invites(codeHash, kind: "account" | "project", userId?, projectId?, role?, createdBy, expiresAt, usedAt)
projects(id, ownerId, name, createdAt, ticketSeq)
members(projectId, userId, role: "owner" | "editor" | "viewer", addedAt)
updates(projectId, seq, bytes, userId, deviceId, at)        -- append-only
snapshots(projectId, bytes, versionJson, uptoSeq, at)       -- compactage toutes les 500 mises à jour
```

Le serveur garde un `LoroDoc` par projet actif en mémoire (déchargé après 10 min sans client).

### 3.2 Client (démon, SQLite local)

```
sync_config(serverUrl, caFile, userId, deviceId, displayName)   -- une seule connexion serveur par workspace
sync_projects(projectId, enabled, role, lastServerVersionJson, lastSyncAt, lastError)
remote_sessions(idHash, deviceName, createdAt, expiresAt, lastSeenAt, revokedAt)   -- §7
```

Clé privée de l'appareil : `SecretStore` (`sync:device`), jamais sur disque en clair.

### 3.3 Changements dans le doc projet

- `Ticket.key: TicketKey | null` et `Ticket.pendingSeq: number | null` (clé provisoire, §5).
- `meta.keyAllocator: "local" | "server"` (défaut `local`).
- `meta.members: LoroMap<userId, { name }>` : annuaire d'affichage, écrit **par le serveur uniquement**.
- `Assignee.ref` d'un humain = `userId` du compte dès que le projet est partagé (migration au premier partage : le nom d'utilisateur local est remplacé par l'`userId` du propriétaire).
- `domains` utilisés par les tickets du projet : copiés dans `projectDomains` (nom, couleur, guidelines) au premier partage, puis édités là. Raison : le doc workspace n'est pas synchronisé et un collègue doit voir les mêmes domaines. **À valider contre le modèle de domaines de la phase 2.**

### 3.4 Ce qui ne se synchronise pas

| Donnée | Où | Raison |
|---|---|---|
| Doc workspace (registre et confiance des composants, préférences) | local | la confiance est propre à la machine (spec B) |
| `folder` du projet, `notesDir`, dépôts et worktrees | local (`project_settings`) | chemins propres à la machine ; `meta.folder` est migré hors du doc au premier partage |
| Runs, hooks, logs, file d'attente, CI, sync d'intégrations | SQLite local | spec §5 (append-only, non collaboratif) ; l'état des runs est diffusé en **présence** (§6) |
| Notes (fichiers `.md`) | disque | spec B §8.2 : les fichiers restent la vérité ; partage par git ou Obsidian Sync |
| Secrets, config MCP | trousseau, local | spec §10 et spec F |
| Code des composants | magasin local | une instance d'un composant absent affiche « Composant absent : id@x.y.z » avec « Installer » (marketplace d'équipe, spec H) |

## 4. Authentification et appareils

- **Pas de mot de passe** : chaque appareil a une paire Ed25519 (WebCrypto). Raison : pas de secret partagé à stocker côté serveur, révocation par appareil.
- Création de compte : l'administrateur exécute `kibo-sync invite account --name "Adam"` ⇒ code à usage unique (128 bits, base32, affiché une fois, stocké haché, 48 h).
- Rejoindre : Paramètres › Sync › « Se connecter à un serveur » : URL + code ⇒ le démon génère la paire, envoie `{ code, publicKey, deviceName }` ⇒ compte et appareil créés.
- Connexion : `GET wss://…/v1/sync` ; premier message serveur `challenge { nonce }` (32 octets) ; client `auth { deviceId, signature(nonce ‖ serverOrigin) }` ; échec ⇒ fermeture 4401. 5 échecs / min / IP ⇒ 429 pendant 5 min.
- Ajouter un appareil : depuis un appareil connecté, « Ajouter un appareil » ⇒ code d'appareil (même mécanisme, 15 min).
- Révocation : `kibo-sync device revoke` ou Paramètres › Sync › Appareils ; les sockets de l'appareil sont fermées immédiatement.

## 5. Clés de ticket concurrentes (décision §12)

**Décision : dans un projet partagé, seul le serveur attribue les clés ; un ticket créé localement reçoit une clé provisoire jusqu'à l'attribution.** Raison : clés plates, contiguës et uniques sans coordination entre pairs ; les plages réservées par pair créeraient des trous et des clés non chronologiques, et demanderaient elles aussi un coordinateur.

1. Projet non partagé (`keyAllocator = local`) : inchangé, le démon attribue (`ticketSeq`).
2. Premier partage : le propriétaire envoie le snapshot ; le serveur importe, fixe `projects.ticketSeq = meta.ticketSeq`, écrit `meta.keyAllocator = "server"` avec son propre pair Loro, et seulement ensuite accepte d'autres membres.
3. Projet partagé : `createTicket` écrit `key: null`, `pendingSeq: n` (compteur local par appareil) ; l'UI affiche `KIB-…` en italique (infobulle « Clé attribuée à la prochaine synchronisation »).
4. Le serveur, à chaque mise à jour importée, cherche les tickets `key === null`, les trie par (horodatage Lamport de création, id), attribue `ticketSeq + 1…` et diffuse ce commit.
5. Invariants vérifiés par le serveur sur chaque mise à jour cliente (fork + `validateProjectUpdate(before, after)`, fonction pure de `core`) : un client n'écrit jamais `key` ni `meta.ticketSeq` ni `meta.keyAllocator` ni `meta.members` ; une clé attribuée ne change plus. Violation ⇒ mise à jour refusée (`UPDATE_REJECTED`), le client resynchronise depuis le serveur (ses modifications locales invalides sont perdues ; seul un client défectueux ou malveillant est concerné).
6. Tant qu'un ticket n'a pas de clé : lancer un agent, générer un message de commit ou une branche à partir de la clé, et mentionner la clé dans une note sont désactivés avec l'infobulle ci-dessus. En ligne, l'attribution prend moins d'une seconde.

## 6. Protocole

WebSocket sur TLS, trames JSON validées par Zod ; les octets Loro en base64. Taille max d'une trame : 8 Mio.

| Sens | Trame | Rôle |
|---|---|---|
| S→C | `challenge { nonce }` | authentification |
| C→S | `auth { deviceId, signature }` | |
| S→C | `welcome { userId, projects: { id, role }[] }` | |
| C→S | `subscribe { projectId, version }` | version = vecteur de versions Loro du client |
| S→C | `update { projectId, bytes, serverSeq }` | ce qui manque au client, puis flux temps réel |
| C→S | `push { projectId, bytes, clientBatchId }` | modifications locales depuis la dernière version connue du serveur |
| S→C | `ack { projectId, clientBatchId, serverSeq }` / `reject { projectId, clientBatchId, code, message }` | |
| C↔S | `presence { projectId, bytes }` | `EphemeralStore` Loro, jamais persisté |
| S→C | `members { projectId, members: { userId, name, role }[] }` | |
| C→S | `share { projectId, snapshot }`, `invite { projectId, role }` → S→C `invite-code { code }` | partage |

- Envoi client : regroupement 50 ms ; hors ligne, rien n'est perdu (le doc local contient tout) ; à la reconnexion, `subscribe` avec la version locale puis `push` de `doc.export({ mode: "update", from: lastServerVersion })`.
- Rôle `viewer` : `push` toujours refusé ; le démon refuse aussi localement toute `ProjectCommand` sur ce projet (`FORBIDDEN`) et l'UI passe le projet en lecture seule.
- `editor` : écrit tout le doc sauf les champs réservés au serveur (§5, point 5). `owner` : en plus, invite, change les rôles, retire des membres, supprime le projet côté serveur.
- Retrait d'un membre : ses sockets pour ce projet sont fermées ; sa copie locale reste lisible, marquée « Accès retiré », non synchronisée.
- Reconnexion : backoff 1 s → 60 s avec gigue.

### 6.1 Présence

État éphémère par appareil : `{ userId, name, pageId | null, ticketId | null, runs: { ticketKey, profile, state }[] }` (délai d'expiration 30 s, rafraîchi toutes les 10 s et à chaque changement). Affichage : avatars des personnes présentes sur le projet (barre supérieure), sur la page et dans le Sheet d'un ticket ouvert par quelqu'un d'autre ; les runs des collègues apparaissent sur les cartes (« opus-dev-1 · Adam ») sans entrer dans la file locale.

### 6.2 Intégrations et sync

Une liaison de sync (spec F §3.2) n'est exécutée que par la machine de `binding.runner` ; les autres membres voient les tickets importés par la sync Loro. Changer de `runner` : action du propriétaire de la liaison ou d'un `owner`.

## 7. Accès distant au démon (opt-in, spec §10)

Distinct de la sync (la sync est une connexion **sortante** ; le démon continue d'écouter sur `127.0.0.1` seulement).

- Désactivé par défaut. Activation dans Paramètres › Sécurité, avec confirmation explicite : choix de l'interface (adresse IP d'une interface locale, jamais `0.0.0.0` par défaut), port, **TLS obligatoire** (certificat auto-signé généré à l'activation, empreinte SHA-256 affichée pour vérification dans le navigateur, ou certificat fourni).
- Appairage distant : code à 6 caractères (écran 31 et Paramètres › Apparence « Générer un code »), valable 5 min, 5 essais max ; échange contre un cookie `Secure; HttpOnly; SameSite=Strict`.
- **Sessions d'appairage persistées** (décision §12) : table `remote_sessions` (hash SHA-256 de l'id, jamais l'id), expiration 30 jours glissants, liste et révocation dans Paramètres › Sécurité. Les sessions locales (`127.0.0.1`) sont aussi persistées, même table, même révocation. Raison : l'UI ne doit plus revenir à l'appairage à chaque redémarrage, et la révocation devient possible.
- `Origin` et `Host` contrôlés contre l'adresse d'écoute distante déclarée ; même CSP qu'en local.

## 8. Chiffrement et sécurité

- Transport : `wss://` obligatoire ; `ws://` accepté seulement vers `127.0.0.1` / `localhost` (tests, dev). Vérification TLS standard, CA supplémentaire possible (`caFile`) pour un serveur auto-hébergé. Serveur : `Bun.serve({ tls })` avec certificat fourni, ou derrière un reverse proxy TLS (le serveur écoute alors sur loopback et l'administrateur le déclare avec `--behind-proxy`).
- Le serveur voit les données en clair (pas de chiffrement de bout en bout, §12).
- **Opt-in explicite du partage** : rien ne quitte la machine tant que l'utilisateur n'a pas (1) configuré un serveur et (2) cliqué « Partager » sur un projet donné, dans un dialogue qui liste ce qui est envoyé et ce qui ne l'est pas (§3.4).
- Invariant « jamais de secret dans le CRDT » vérifié par un test qui cherche les secrets factices dans les snapshots serveur.
- Quotas serveur : 50 Mio par projet, 100 mises à jour / s par appareil, 20 connexions par utilisateur.
- Journal d'audit serveur (append-only) : connexions, invitations, changements de rôle, rejets.

## 9. Tests

| Niveau | Cas |
|---|---|
| core | `validateProjectUpdate` : chaque invariant du §5, point 5 ; attribution des clés : déterministe pour un même ensemble de tickets en attente |
| propriétés (fast-check) | N clients (2 à 5), opérations aléatoires sur tickets, pages, liens, partitions réseau et reconnexions aléatoires ⇒ convergence de tous les docs vers le serveur ; **toutes les clés uniques et contiguës** ; chaque ticket finit avec une clé |
| serveur | authentification (signature valide, rejouée, appareil révoqué), invitations (expirée, réutilisée), rôles (viewer refusé, editor sur champ réservé refusé), compactage snapshot, quotas |
| démon | partage d'un projet existant (migrations `folder` et `Assignee.ref`), mode lecture seule viewer, hors ligne puis rattrapage, `UPDATE_REJECTED` ⇒ resynchronisation |
| présence | expiration, affichage d'un run distant |
| TLS | serveur de test avec certificat de test auto-signé (fixture versionnée, clé de test uniquement) et `caFile` ; refus d'un `ws://` non loopback |
| accès distant | désactivé par défaut ; code à 6 caractères (expiration, essais) ; sessions persistées et révoquées |
| e2e | Playwright avec deux contextes navigateur sur deux démons et un serveur local : création d'un ticket chez A visible chez B en < 1 s, clé provisoire puis définitive, avatars de présence |

Aucun serveur distant ni compte réel en CI : serveur et démons démarrent dans le processus de test sur des ports loopback.

## 10. Critères de sortie

- Propriété de convergence et d'unicité des clés verte en CI (≥ 200 exécutions par CI).
- Scénario e2e à deux utilisateurs vert sur macOS et Linux.
- Un projet non partagé se comporte exactement comme en v0.6 (tests existants inchangés).
- Écrans de sync conformes à leurs maquettes (à dessiner, §11), en sombre et en clair.

## 11. Écrans à dessiner dans Penpot avant implémentation

Aucun écran de la sync n'existe : Paramètres › Sync (serveur, compte, appareils), dialogue « Partager le projet » (ce qui part / ne part pas, rôles, code d'invitation), « Rejoindre un projet », avatars de présence (barre, page, Sheet), ticket à clé provisoire, projet en lecture seule, « Accès retiré », composant absent, Paramètres › Sécurité (accès distant, sessions).

## 12. Hors périmètre

- Chiffrement de bout en bout (le serveur lit les données) ; à rouvrir si un serveur tiers est utilisé.
- Fédération ou plusieurs serveurs par workspace ; sync du doc workspace ; sync des notes.
- Comptes par OAuth ou SSO ; hébergement géré du serveur.
- Permissions plus fines que le projet (par page, par ticket).

## 13. Décisions d'implémentation (plan de phase 7)

Reprises du plan `docs/superpowers/plans/2026-09-26-kibo-sync-marketplace.md` (« Décisions nouvelles »), recalées sur le code de v0.6 par la tâche 0 ; la numérotation (D1 à D39) est celle du plan, les décisions qui relèvent de la marketplace et du durcissement sont dans la spec H §13. Elles complètent les silences de cette spec sans la contredire ; §3.3 « À valider contre le modèle de domaines de la phase 2 » est tranché par la tâche 7 du plan (`ShareMigrationInput`) (domaines `{ id, name, color }` et leurs guidelines copiés dans `projectDomains`).

- **D2** · **Certificats générés par un encodeur X.509 minimal** (ECDSA P-256, WebCrypto) plutôt qu'une fixture versionnée (spec G §9) ou le binaire `openssl` : aucune clé dans le dépôt, aucune dépendance, et le même code sert au certificat auto-signé de l'accès distant (spec G §7).
- **D3** · **Protocole** (spec G §6) complété : `update` et `ack` portent `version` (vecteur de versions du serveur, base de l'envoi suivant) ; `reject` porte `version` et le code `OUT_OF_DATE` (dépendances manquantes : le client renvoie depuis cette version, sans perte) ; trames ajoutées `unsubscribe`, `redeem` / `joined`, `set-role` (rôle `null` = retrait), `unshare`, `revoked`, `device-invite`, `list-devices` / `devices`, `revoke-device`, `done`, `error`, chacune corrélée par `requestId`. Invitations de kind `device` (spec G §4 « même mécanisme »). Invitation de projet valable 48 h.
- **D4** · **Défi d'authentification** : signature Ed25519 de `"kibo-sync-v1\n" + nonce + "\n" + origin`, où `origin` est l'origine publique déclarée du serveur (`--origin`).
- **D6** · **Clé provisoire** : `pendingSeq = 1 + max(pendingSeq des tickets créés par ce pair Loro)`, calculé dans le doc (pas d'I/O). Ordre d'attribution = (Lamport de l'opération de création du nœud, id), le Lamport étant `change.lamport + (id.counter − change.counter)`.
- **D7** · **Partage atomique côté démon** : pendant `shareProject`, les commandes sur ce projet échouent en `CONFLICT` (« partage en cours ») ; les migrations (dossier, assignés, domaines, liaisons) sont appliquées au doc **avant** l'export du snapshot, pour que le dossier local ne parte jamais.
- **D8** · **Resynchronisation après `UPDATE_REJECTED`** : le démon remplace le doc local par un doc neuf construit depuis le serveur (`subscribe` avec `version: null`) ; les modifications locales non acceptées sont perdues (spec G §5.5).
- **D9** · **Lecture seule locale** pour un `viewer` et pour un projet « Accès retiré » : toute `ProjectCommand` échoue en `FORBIDDEN`, même hors ligne.
- **D10** · **Présence authentifiée** : le serveur n'accepte une trame de présence que si elle ne touche que la clé de l'appareil émetteur et que `userId` y est celui de la session ; il renvoie l'état courant (`encodeAll`) à chaque nouvel abonné.
- **D17** · **RPC sensibles réservées aux sessions locales** (`127.0.0.1`) : `enableRemoteAccess`, `disableRemoteAccess`, `createPairingCode`, `setAllowUnsandboxed`, `connectSyncServer`, `disconnectSyncServer`, `addMarketSource`, `unpinPublisher` ⇒ `FORBIDDEN` depuis une session distante. L'appairage distant se fait par code à 6 caractères seulement (jamais par le jeton).
- **D18** · **Clé privée TLS de l'accès distant** dans `SecretStore` (`remote:tls`), certificat en `<KIBO_HOME>/remote/cert.pem` (`0600`). `SecretName` accepte **trois noms système exacts** (`sync:device`, `market:publisher`, `remote:tls`) en plus des noms d'intégration ; un composant ne peut déclarer qu'un secret d'intégration (`IntegrationSecretNameSchema` dans le manifeste), jamais un secret système.
- **D19** · **Présence exposée aux composants** : `sdk.presence.list()` (appel `presence.list`, soumis à `reads: ticket`) et `members` dans l'instantané, pour que le Kanban affiche « opus-dev-1 · Adam » et le nom d'un assigné identifié par `userId`.
- **D20** · **Paramètres** : nouvelles sections « Sync » (après Intégrations), « Sécurité » (entrée existante, activée) et « Composants › Sources », chacune une valeur de l'enum `Screen` (`sync`, `security`, `sources`) ; l'entrée « Apparence » est activée avec le seul bloc « Accès web » de l'écran 15 (`appearance`).
- **D21** · **`kibo-sync`** est compilé par `bun build --compile` (`packages/sync-server/scripts/build.ts`), hors bundle Tauri. La source d'équipe est servie sous `<serveur>/market/` (`index.json`, `index.json.sig`, `packages/<id>/<version>.kpkg`).
- **D22** · **Clé de projet en double** : rejoindre un projet dont la clé existe déjà localement échoue en `INVALID_INPUT` avec un message explicite (« Un projet local utilise déjà la clé KIB ») ; le renommage de clé est hors périmètre v1.0.
- **D25** · **`TicketView.keyLabel`** calculé par `readProject` (« KIB-12 » ou « KIB-… ») : l'affichage ne recompose jamais une clé (T6).
- **D26** · **Tests d'intégration du démon contre le vrai serveur** : `@kibo/sync-server` est une `devDependency` du démon, importée seulement par les fichiers `*.test.ts` et `testing/` ; aucun code de production du démon ne l'importe (contrôlé par un test qui parcourt les imports de `packages/daemon/src` hors tests).
- **D27** · **Noms déjà pris** : `Role` (onboarding IA), `SyncState` (sync d'intégrations) et le dossier `packages/daemon/src/sync/` (sync d'intégrations) existent ; la phase 7 utilise `MemberRole`, `SyncConnectionState` et `packages/daemon/src/collab/`. Les tables client gardent les noms de la spec G (`sync_config`, `sync_projects`), sans collision.
- **D28** · **Événements de la phase 7** : variantes de `ChangeMessage` émises par `service.docs.emit`, nommées `collab.changed`, `presence.changed`, `market.changed`, `sessions.changed`, `sandbox.changed` (le type `sync` est pris) ; le client les reçoit par `KiboClient.subscribeEvents`, aiguillés avant les écouteurs de projet pour ne jamais recharger la liste des projets.
- **D29** · **Branchement du démon** : `service.ts` (300 lignes) ne reçoit plus de méthodes RPC ; chaque sous-système (`sandbox`, `remote`, `market`, `collab`) a son `bootstrap.ts` et se branche dans `assemble` (`daemon.ts`) par une extension ou un gestionnaire RPC (T9). `main.ts` ne lit que des options (`KIBO_MARKET_ALLOW_LOOPBACK`).
- **D30** · **Garde d'écriture par projet** (T21) : `docs.assertWritable(projectId)` est appelé par le chemin des commandes (`guarded` de `command-path.ts`) **et** par les deux écritures qui le contournent (`writeInstanceData` des composants, `updateInstance`) : la lecture seule (décision 9) et le verrou de partage (décision 7) couvrent toutes les écritures.
- **D31** · **Identité locale d'un projet partagé** (T23) : `docs.identity(projectId)` vaut l'`userId` du compte de sync pour un projet partagé, le nom d'utilisateur OS sinon ; elle sert au `runner` et au `createdBy` des liaisons (spec G §6.2), à l'assigné humain et au `viewer` des composants (filtre « Moi + agents », « Mes tickets »).
- **D32** · **Dossier local d'un projet partagé** (T23) : `meta.folder` quitte le doc au partage et vit dans `project_settings(projectId, "folder")` ; `docs.projectMeta` le réinjecte pour `getProject`, le contexte des agents (worktrees), les notes et le code. La copie du dossier dans la liste `projects` du workspace est conservée : elle est lue hors du doc projet (vue d'ensemble, « Mes tickets », palette) et le doc workspace ne quitte jamais la machine.
- **D33** · **Erreurs de la sync côté démon** : `SyncStatus.lastError` et `SyncProjectStatus.lastError` portent un code stable (`UNAUTHORIZED`, `DEVICE_REVOKED`, `ACCESS_REVOKED`, `SYNC_OFFLINE`, `TLS_REQUIRED`…), traduit par l'UI dans `fr-collab.ts` ; aucun texte français dans le démon (règle de `CLAUDE.md`).
- **D36** · **Sessions de la CLI** : chaque commande `kibo` qui appaire par le jeton crée une session persistée « Commande kibo » (30 jours glissants, révocable) ; la réutilisation d'un cookie par la CLI est hors périmètre v1.0.
- **D37** · **Accès distant et widgets sandboxés** (choix du chef d'équipe, délégué par Adam) : le serveur des iframes sandboxées reste sur `127.0.0.1` ; à distance, l'UI, les composants intégrés et les composants de confiance fonctionnent, les widgets sandboxés ne se chargent pas (message dans le cadre de l'instance). Limite documentée de la v1.0 (T13, T25, rapport du jalon).
- **D38** · **Écran 15 réduit** (choix du chef d'équipe, délégué par Adam) : l'entrée « Apparence » des Paramètres est activée avec le seul bloc « Accès web » (générer un code d'appairage) ; le reste de l'écran 15 est un écart listé au jalon (T25).
- **D39** · **Champs figés au partage** (choix du chef d'équipe) : une fois le projet partagé, `meta.id` et `meta.key` sont immuables (`validateProjectUpdate` refuse toute modification en `UPDATE_REJECTED`, même par l'`owner`) ; `meta.folder` est un chemin local qui ne vit pas dans le doc partagé : `migrateForSharing` le retire du doc (T23 le range dans `project_settings`) et `validateProjectUpdate` refuse sa réapparition, même à `null`. `migrateForSharing` refuse un doc déjà partagé (`keyAllocator = server`) en `INVALID_INPUT`. Raison : changer le préfixe casse toutes les clés et mentions existantes, changer l'id casse l'identité du projet, et un chemin local ne concerne qu'une machine. Précision (T7) : dans `meta`, un éditeur ne peut modifier que `name` et `color`, et une valeur modifiée doit respecter `ProjectMeta` ; tout autre champ de `meta` ne peut être ni ajouté ni modifié (`UPDATE_REJECTED`).
