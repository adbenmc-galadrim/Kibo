# Kibo — Spec E : IA dans le produit (phase 6)

- **Date** : 2026-09-26 · **Phase** : 6 (v0.6) · **Statut** : à valider
- **Parent** : `2026-09-25-kibo-design.md` §2 (zéro token pour l'état), §6 « Création », §7, §11, §12 · **Maquettes** : écrans 19, 29, 30, 6
- **Suppose livrés** : phase 2 (file d'attente, profils, runner `claude` headless, hooks à jeton par run avec réponse `PreToolUse`, `--resume`, faux binaire `claude`) ; phase 4 (`packages/devkit` : générateur, build, validation, `inferPermissions` ; registre ; écran 30 ; publication écran 6).

## 1. Objectif

Deux usages de l'IA, **sur l'abonnement Claude de l'utilisateur** via `claude` en headless, jamais pour décider d'un état :
1. **Assistant d'onboarding** : à partir du rôle de l'utilisateur, proposer les pages et composants de départ d'un projet.
2. **Génération de composants** : décrire un composant, laisser un agent écrire le code dans le squelette du générateur, valider de façon déterministe, faire relire, puis enregistrer.

## 2. Périmètre

- Profils système `assistant` et `generateur` (modifiables : modèle seulement), exécutés comme tout run via la file d'attente.
- Onboarding : presets déterministes par rôle + suggestion IA optionnelle à partir d'un texte libre.
- Génération : création (écran 29, colonne IA) et « Modifier avec l'IA » d'un composant utilisateur existant (aboutit au dialogue de publication, écran 6).
- Extension du faux `claude` (écriture de fichiers, sortie JSON) pour tester tout cela sans tokens.

## 3. Principes

- **Tout appel à `claude` est un run de la file** (CLAUDE.md : « tout run passe par la file d'attente, sans exception »). Il affiche son état dans la barre et le tiroir des agents, consomme un créneau, peut passer en `waiting_input`.
- **Rien de ce que dit le modèle ne change un état** : le passage d'une étape à l'autre vient des événements du run (`Stop`), des fichiers écrits et du rapport de validation calculé par du code.
- **L'IA ne remplit que `ui.tsx`, `server.ts` et les tests** (spec §6). Manifeste, `migrations.ts`, `tsconfig.json`, `package.json` : écrits par Kibo seul.
- **Hors ligne ou `claude` absent** : l'onboarding retombe sur les presets ; la génération est désactivée avec l'explication (« claude introuvable » / « hors ligne »).

## 4. Modèle de données

### 4.1 Profils système (table des profils de la phase 2)

| Id | Outils Claude Code | Mode de permissions | Espace de travail | Parallèle |
|---|---|---|---|---|
| `assistant` | aucun (`--tools ""`, ou `--disallowedTools` de tous les outils selon la version installée ; vérifié au premier lancement) | `default` | dossier temporaire vide | 1 |

Modèle par défaut : celui du profil par défaut de l'utilisateur. Jamais `--dangerously-skip-permissions`.

### 4.2 Brouillon de composant

`<KIBO_HOME>/components/drafts/<draftId>/` (`0700`), créé par `devkit.scaffold` puis rempli par l'agent :

```
kibo.component.json   (Kibo)        ui.tsx          (IA)
tsconfig.json         (Kibo)        server.ts       (IA, optionnel)
package.json          (Kibo)        *.test.tsx      (IA ; component.test.tsx garde l'appel à runConformance)
CLAUDE.md             (Kibo : règles)   .claude/skills/kibo-component/SKILL.md (Kibo : procédure et API du SDK)
```

Table SQLite `component_drafts(id, componentId, mode: "create" | "modify", baseVersion, description, runId, sessionId, status, attempts, reportJson, createdAt, updatedAt)` avec `status ∈ describing | generating | validating | failed | review | permissions | done | abandoned`. État dérivé uniquement des événements du run et du rapport de validation.

### 4.3 Onboarding

```ts
export const Role = z.enum(["dev", "designer", "pm", "other"]);
export const StarterPlan = z.object({

    title: z.string().min(1).max(40),
    kind: PageKind,

```

Presets (dans `packages/ui/src/onboarding/presets.ts`, déterministes) :

| Rôle | Pages proposées |
|---|---|
| Développeur·se | Tableau de bord (Kanban, Mes tickets, Graphe · widget), Kanban (vue), Tickets (vue), Graphe (vue), Notes (vue) |
| Designer | Tableau de bord (Tickets filtrés sur moi, Notes · widget), Kanban (vue), Notes (vue) |
| Chef·fe de projet | Tableau de bord (Kanban, Graphe · widget chemin critique), Tickets (vue), Graphe (vue) |

Un composant absent du catalogue est retiré du preset. « Changements » n'y figure pas : c'est une vue fixe du shell, présente d'office quand le projet a un dépôt git (spec phase 3 §10).

## 5. Flux

### 5.1 Assistant d'onboarding

1. Écran 19 (Bienvenue) → « Créer mon premier projet » ouvre le Nouveau projet (écran 2) avec une étape **« Ton rôle »** avant « Point de départ » : 4 choix + champ facultatif « Décris ton usage en une phrase ».
2. Sans texte (ou rôle ≠ Autre) : le preset s'affiche aussitôt, **sans IA**, sous forme de liste de pages cochables avec leurs composants.
3. Avec texte : bouton « Proposer avec Claude » ⇒ run `assistant` mis en file avec :
   - un prompt fixe (FR) contenant la liste des composants installés (`id`, titre, description, `kind`), les types de page, le rôle et le texte de l'utilisateur, et l'instruction de répondre par un objet `StarterPlan` ;
   - `--output-format json` et, si la version de `claude` le permet, `--json-schema` avec le schéma JSON de `StarterPlan`.
4. Le résultat est parsé par Zod ; les composants inconnus sont retirés ; si rien de valide ne reste, ou en cas d'échec, de délai (60 s) ou d'annulation : le preset reste affiché avec le message « Suggestion indisponible, voici le point de départ standard ».
5. L'utilisateur coche / décoche, renomme, puis crée : le projet est créé et les pages et instances sont ajoutées par les commandes existantes (`addPage`, `addInstance`) — l'IA n'écrit jamais dans le doc.
6. L'assistant est relançable depuis la Vue d'ensemble vide (écran 26) et le dialogue Nouvelle page (« Suggérer des pages »), avec le même flux.

### 5.2 Générer un composant (écran 29, colonne « Décrire à l'IA »)

Étapes affichées en bas du dialogue : **1 · Décrire → 2 · Générer (agent) → 3 · Tests de conformité → 4 · Permissions → 5 · Ajouter à la page**.

1. **Décrire** : « Ce que doit faire le composant » (texte, 20 à 2000 caractères), titre (proposé : premiers mots, modifiable), `id` (slug du titre, unique, modifiable), type (widget / vue / les deux), « Avec backend » (case, décochée). Bouton « Générer avec un agent » (orange, action d'agent).
2. **Générer** : `devkit.scaffold` crée le brouillon ; un run `generateur` est mis en file (`cwd` = brouillon) avec le prompt : description, type, règles de `CLAUDE.md` du brouillon, et la consigne de lancer `kibo component test` avant de s'arrêter. Suivi par la timeline des hooks ; question de l'agent ⇒ `waiting_input` et champ « Répondre » comme pour tout run.
   - **Garde-fou déterministe** : le hook `PreToolUse` du run renvoie `permissionDecision: "deny"` pour tout `Edit`/`Write` hors de `ui.tsx`, `server.ts`, `*.test.tsx` du brouillon (chemins résolus, liens symboliques refusés), et pour toute commande `Bash` autre que `kibo component test`.
   - À `Stop`, Kibo vérifie que les fichiers réservés à Kibo sont identiques à leur version générée (hash) ; sinon ils sont restaurés et l'incident est noté dans le rapport.
3. **Tests de conformité** : `devkit.validateComponent` (typecheck, tests, conformance, permissions). Le rapport s'affiche par section (vert / rouge, sortie repliable).
   - Échec : « Corriger avec l'agent » relance la même session (`--resume`) avec le rapport en message, **3 tentatives au total** ; ensuite seuls « Ouvrir le dossier dans l'éditeur » (chemin mode code, `kibo component test` à la main) et « Abandonner » restent.
   - Succès : vue **Relire le diff** (fichiers écrits par l'agent, en lecture, composant Diff de la phase 3), obligatoire avant de continuer.
4. **Permissions** : les permissions **utilisées** (`inferPermissions` ∪ usages enregistrés par la conformité) sont écrites par Kibo dans le manifeste du brouillon, puis l'écran 30 s'affiche (« Composant généré par IA · empreinte sha256 … · vérifiée par le démon », Sandboxé recommandé et présélectionné).
5. **Ajouter à la page** : publication `0.1.0` (origine `ai`, sources copiées du brouillon vers `components/src/<id>/` puis magasin), approbation avec le niveau choisi, `addInstance` sur la page courante. Brouillon supprimé.

### 5.3 Modifier un composant avec l'IA

1. Menu `⋯` d'un composant utilisateur (page Composants ou instance) → « Modifier avec l'IA » : champ « Ce qu'il faut changer ».
2. Brouillon `mode: "modify"` copié de `components/src/<id>/` ; même garde-fou et même validation.
3. Version proposée : `patch` si ni permissions ni `configVersion` ne changent, sinon `minor` ; modifiable. `changes` du manifeste = la demande de l'utilisateur (une ligne), éditable.
4. Si la config change de forme, l'agent n'a pas le droit d'écrire `migrations.ts` : la validation échoue avec « configSchema modifié : ajoute une migration » et la main passe au mode code. Raison : une migration de données est trop risquée pour une génération non relue ligne à ligne.
5. Fin : dialogue de publication (écran 6) avec usages, changements, nouvelles permissions, « Mettre à jour partout » / « Créer une nouvelle version ».

## 6. Contrats

RPC ajoutées :

| Méthode | Entrée | Sortie |
|---|---|---|
| `suggestStarter` | `{ role: Role, text: string }` | `{ runId }` ; le résultat arrive par l'événement `starter.ready { runId, plan: StarterPlan \| null }` sur le WebSocket |
| `startComponentDraft` | `{ mode: "create", id, title, kind, withServer, description } \| { mode: "modify", id, description }` | `ComponentDraft` |
| `retryComponentDraft` | `{ draftId }` | `ComponentDraft` |
| `getComponentDraft` | `{ draftId }` | `ComponentDraft & { report: ValidationReport \| null, diff: FileDiff[] }` |
| `finalizeComponentDraft` | `{ draftId, version, hash, trust, target: { projectId, pageId } \| null }` | `PublishResult` ; `HASH_MISMATCH` si le brouillon a changé depuis l'affichage |
| `abandonComponentDraft` | `{ draftId }` | `null` |

Le brouillon n'est lisible et modifiable que par le démon ; le run l'édite via Claude Code sous garde-fou. Nouveau code d'erreur : `AI_UNAVAILABLE` (`claude` absent, non connecté, ou profil désactivé).

## 7. Sécurité

- L'agent générateur n'a ni réseau (outils web interdits), ni shell libre, ni écriture hors des trois cibles ; le garde-fou est exécuté par le démon (hook), pas confié au modèle.
- Le code généré suit **exactement** le chemin d'un code tiers : validation, empreinte, écran 30, sandbox par défaut. Aucune confiance implicite parce que « Kibo l'a généré ».
- Le prompt ne contient ni secret, ni contenu de tickets (seulement la description saisie et l'API publique du SDK). L'assistant d'onboarding ne reçoit que rôle, texte et catalogue.
- Sorties du modèle validées par Zod (onboarding) ou par le validateur (génération). Le code généré ne s'exécute que dans `kibo component test` / la validation, avec les restrictions de la phase 4 (imports interdits refusés au build, `bun test --preload restrict.ts` sans réseau, fichiers ni processus, SDK simulé) ; en phase 7, aussi dans le bac à sable OS.

## 8. Tests (zéro token)

- **Faux `claude`** (phase 2) étendu avec deux actions de scénario : `write { path, fixture }` (écrit un fichier via un événement `PreToolUse`/`PostToolUse` réaliste, soumis au garde-fou) et `result { json }` (sortie `--output-format json`). Fixtures dans `packages/daemon/src/testing/claude-scenarios/`.
- Scénarios :
  1. génération réussie du premier coup ⇒ `review` ⇒ finalisation ⇒ instance sur la page ;
  2. premier essai qui échoue au typecheck, second réussi (`--resume` avec le rapport) ;
  3. trois échecs ⇒ bouton « Corriger avec l'agent » désactivé ;
  4. tentative d'écriture de `kibo.component.json` et de `../evil.ts` ⇒ refusées par le hook ; modification directe détectée à `Stop` ⇒ restaurée ;
  5. code qui utilise `sdk.fetch` non déclaré ⇒ permission inférée et affichée à l'écran 30 ; argument non littéral ⇒ échec de validation ;
  6. onboarding : JSON valide ⇒ plan ; JSON invalide, composant inconnu, délai ⇒ preset.
- Unitaires : presets (composants absents retirés), calcul de version proposée, hash des fichiers réservés.
- e2e Playwright : écran 29 (IA) de bout en bout avec le faux `claude`, en sombre et en clair ; étape « Ton rôle » avec preset.

## 9. Critères de sortie

- Les scénarios 1 à 6 passent en CI macOS et Linux sans réseau ni token.
- Le composant généré par le faux agent est rendu sandboxé sur une page et passe la conformité.
- Écrans 29 (les deux colonnes) et 30 conformes en sombre et en clair ; étape « Ton rôle » conforme à sa maquette.

## 10. Écrans à dessiner dans Penpot avant implémentation

Étape « Ton rôle » du Nouveau projet (avec liste de pages cochables et état « Suggestion indisponible ») ; étapes 2 et 3 du dialogue écran 29 (run en cours, rapport de validation, échec après 3 tentatives, relecture du diff) ; saisie « Modifier avec l'IA ».

## 11. Hors périmètre

- Génération de `migrations.ts` par l'IA ; génération de composants dans le monorepo Kibo lui-même.
- Tout appel à l'API Anthropic avec une clé : seul l'abonnement via `claude` est utilisé.
- Assistant conversationnel général, résumé de tickets, génération de tickets (non prévus par la spec).

## Comptes et secrets réels

Aucun pour la CI. Un essai manuel de bout en bout demande un `claude` connecté à l'abonnement d'Adam (consomme ses tokens).
