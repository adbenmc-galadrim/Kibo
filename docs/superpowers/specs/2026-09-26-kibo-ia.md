# Kibo — Spec E : IA dans le produit (phase 6)

- **Date** : 2026-09-26 · **Phase** : 6 (v0.6) · **Statut** : à valider
- **Parent** : `2026-09-25-kibo-design.md` §2 (zéro token pour l'état), §6 « Création », §7, §11, §12 · **Maquettes** : écrans 19, 29, 30, 6
- **Décisions du plan** : §12 (I1 à I46), qui priment sur le texte des sections précédentes.
- **Suppose livrés** : phase 2 (file d'attente, profils, runner `claude` headless, hooks à jeton par run avec réponse `PreToolUse`, `--resume`, faux binaire `claude`) ; phase 4 (`packages/devkit` : générateur, build, validation, `inferPermissions` ; registre ; écran 30 ; publication écran 6).

## 1. Objectif

Deux usages de l'IA, **sur l'abonnement Claude de l'utilisateur** via `claude` en headless, jamais pour décider d'un état :
1. **Assistant d'onboarding** : à partir du rôle de l'utilisateur, proposer les pages et composants de départ d'un projet.
2. **Génération de composants** : décrire un composant, laisser un agent écrire le code dans le squelette du générateur, valider de façon déterministe, faire relire, puis enregistrer.

## 2. Périmètre

- Profils système `assistant` et `generateur` (modifiables : modèle seulement), exécutés comme tout run via la file d'attente.
- Onboarding : presets déterministes par rôle + suggestion IA optionnelle à partir d'un texte libre.
- Génération : création (écran 29, colonne IA) et « Modifier avec l'IA » d'un composant utilisateur existant (aboutit au dialogue de publication, écran 6).
- Extension du faux `claude` (écriture de fichiers, sortie JSON) pour tester tout cela sans tokens.

## 3. Principes

- **Tout appel à `claude` est un run de la file** (CLAUDE.md : « tout run passe par la file d'attente, sans exception »). Il affiche son état dans la barre et le tiroir des agents, consomme un créneau, peut passer en `waiting_input`.
- **Rien de ce que dit le modèle ne change un état** : le passage d'une étape à l'autre vient des événements du run (`Stop`), des fichiers écrits et du rapport de validation calculé par du code.
- **L'IA ne remplit que `ui.tsx`, `server.ts` et les tests** (spec §6). Manifeste, `migrations.ts`, `tsconfig.json`, `package.json` : écrits par Kibo seul.
- **Hors ligne ou `claude` absent** : l'onboarding retombe sur les presets ; la génération est désactivée avec l'explication (« claude introuvable » / « hors ligne »).

## 4. Modèle de données

### 4.1 Profils système (table des profils de la phase 2)

| `assistant` | aucun (`--tools ""`, ou `--disallowedTools` de tous les outils selon la version installée ; vérifié au premier lancement) | `default` | dossier temporaire vide | 1 |

Modèle par défaut : celui du profil par défaut de l'utilisateur. Jamais `--dangerously-skip-permissions`.

### 4.2 Brouillon de composant

`<KIBO_HOME>/components/drafts/<draftId>/` (`0700`), créé par `devkit.scaffold` puis rempli par l'agent :

```
kibo.component.json   (Kibo)        ui.tsx          (IA)
tsconfig.json         (Kibo)        server.ts       (IA, optionnel)
package.json          (Kibo)        *.test.tsx      (IA ; component.test.tsx garde l'appel à runConformance)
CLAUDE.md             (Kibo : règles)   .claude/skills/kibo-component/SKILL.md (Kibo : procédure et API du SDK)
```

Table SQLite `component_drafts(id, componentId, mode: "create" | "modify", baseVersion, description, runId, sessionId, status, attempts, reportJson, createdAt, updatedAt)` avec `status ∈ describing | generating | validating | failed | review | permissions | done | abandoned`. État dérivé uniquement des événements du run et du rapport de validation.

## 5. Flux

### 5.1 Assistant d'onboarding

1. Écran 19 (Bienvenue) → « Créer mon premier projet » ouvre le Nouveau projet (écran 2) avec une étape **« Ton rôle »** avant « Point de départ » : 4 choix + champ facultatif « Décris ton usage en une phrase ».
2. Sans texte (ou rôle ≠ Autre) : le preset s'affiche aussitôt, **sans IA**, sous forme de liste de pages cochables avec leurs composants.
3. Avec texte : bouton « Proposer avec Claude » ⇒ run `assistant` mis en file avec :
   - un prompt fixe (FR) contenant la liste des composants installés (`id`, titre, description, `kind`), les types de page, le rôle et le texte de l'utilisateur, et l'instruction de répondre par un objet `StarterPlan` ;
   - `--output-format json` et, si la version de `claude` le permet, `--json-schema` avec le schéma JSON de `StarterPlan`.
4. Le résultat est parsé par Zod ; les composants inconnus sont retirés ; si rien de valide ne reste, ou en cas d'échec, de délai (60 s) ou d'annulation : le preset reste affiché avec le message « Suggestion indisponible, voici le point de départ standard ».
5. L'utilisateur coche / décoche, renomme, puis crée : le projet est créé et les pages et instances sont ajoutées par les commandes existantes (`addPage`, `addInstance`) — l'IA n'écrit jamais dans le doc.
6. L'assistant est relançable depuis la Vue d'ensemble vide (écran 26) et le dialogue Nouvelle page (« Suggérer des pages »), avec le même flux.

### 5.2 Générer un composant (écran 29, colonne « Décrire à l'IA »)

Étapes affichées en bas du dialogue : **1 · Décrire → 2 · Générer (agent) → 3 · Tests de conformité → 4 · Permissions → 5 · Ajouter à la page**.

1. **Décrire** : « Ce que doit faire le composant » (texte, 20 à 2000 caractères), titre (proposé : premiers mots, modifiable), `id` (slug du titre, unique, modifiable), type (widget / vue / les deux), « Avec backend » (case, décochée). Bouton « Générer avec un agent » (orange, action d'agent).
2. **Générer** : `devkit.scaffold` crée le brouillon ; un run `generateur` est mis en file (`cwd` = brouillon) avec le prompt : description, type, règles de `CLAUDE.md` du brouillon, et la consigne de lancer `kibo component test` avant de s'arrêter. Suivi par la timeline des hooks ; question de l'agent ⇒ `waiting_input` et champ « Répondre » comme pour tout run.
   - **Garde-fou déterministe** : le hook `PreToolUse` du run renvoie `permissionDecision: "deny"` pour tout `Edit`/`Write` hors de `ui.tsx`, `server.ts`, `*.test.tsx` du brouillon (chemins résolus, liens symboliques refusés), et pour toute commande `Bash` autre que `kibo component test`.
   - À `Stop`, Kibo vérifie que les fichiers réservés à Kibo sont identiques à leur version générée (hash) ; sinon ils sont restaurés et l'incident est noté dans le rapport.
3. **Tests de conformité** : `devkit.validateComponent` (typecheck, tests, conformance, permissions). Le rapport s'affiche par section (vert / rouge, sortie repliable).
   - Échec : « Corriger avec l'agent » relance la même session (`--resume`) avec le rapport en message, **3 tentatives au total** ; ensuite seuls « Ouvrir le dossier dans l'éditeur » (chemin mode code, `kibo component test` à la main) et « Abandonner » restent.
   - Succès : vue **Relire le diff** (fichiers écrits par l'agent, en lecture, composant Diff de la phase 3), obligatoire avant de continuer.
4. **Permissions** : les permissions **utilisées** (`inferPermissions` ∪ usages enregistrés par la conformité) sont écrites par Kibo dans le manifeste du brouillon, puis l'écran 30 s'affiche (« Composant généré par IA · empreinte sha256 … · vérifiée par le démon », Sandboxé recommandé et présélectionné).
5. **Ajouter à la page** : publication `0.1.0` (origine `ai`, sources copiées du brouillon vers `components/src/<id>/` puis magasin), approbation avec le niveau choisi, `addInstance` sur la page courante. Brouillon supprimé.

### 5.3 Modifier un composant avec l'IA

1. Menu `⋯` d'un composant utilisateur (page Composants ou instance) → « Modifier avec l'IA » : champ « Ce qu'il faut changer ».
2. Brouillon `mode: "modify"` copié de `components/src/<id>/` ; même garde-fou et même validation.
3. Version proposée : `patch` si ni permissions ni `configVersion` ne changent, sinon `minor` ; modifiable. `changes` du manifeste = la demande de l'utilisateur (une ligne), éditable.
4. Si la config change de forme, l'agent n'a pas le droit d'écrire `migrations.ts` : la validation échoue avec « configSchema modifié : ajoute une migration » et la main passe au mode code. Raison : une migration de données est trop risquée pour une génération non relue ligne à ligne.
5. Fin : dialogue de publication (écran 6) avec usages, changements, nouvelles permissions, « Mettre à jour partout » / « Créer une nouvelle version ».

## 6. Contrats

RPC ajoutées :

| Méthode | Entrée | Sortie |
|---|---|---|
| `suggestStarter` | `{ role: Role, text: string }` | `{ runId }` ; le résultat arrive par l'événement `starter.ready { runId, plan: StarterPlan \| null }` sur le WebSocket |
| `startComponentDraft` | `{ mode: "create", id, title, kind, withServer, description } \| { mode: "modify", id, description }` | `ComponentDraft` |
| `retryComponentDraft` | `{ draftId }` | `ComponentDraft` |
| `getComponentDraft` | `{ draftId }` | `ComponentDraft & { report: ValidationReport \| null, diff: FileDiff[] }` |
| `finalizeComponentDraft` | `{ draftId, version, hash, trust, target: { projectId, pageId } \| null }` | `PublishResult` ; `HASH_MISMATCH` si le brouillon a changé depuis l'affichage |
| `abandonComponentDraft` | `{ draftId }` | `null` |

Le brouillon n'est lisible et modifiable que par le démon ; le run l'édite via Claude Code sous garde-fou. Nouveau code d'erreur : `AI_UNAVAILABLE` (`claude` absent, non connecté, ou profil désactivé).

## 7. Sécurité

- L'agent générateur n'a ni réseau (outils web interdits), ni shell libre, ni écriture hors des trois cibles ; le garde-fou est exécuté par le démon (hook), pas confié au modèle.
- Le code généré suit **exactement** le chemin d'un code tiers : validation, empreinte, écran 30, sandbox par défaut. Aucune confiance implicite parce que « Kibo l'a généré ».
- Le prompt ne contient ni secret, ni contenu de tickets (seulement la description saisie et l'API publique du SDK). L'assistant d'onboarding ne reçoit que rôle, texte et catalogue.
- Sorties du modèle validées par Zod (onboarding) ou par le validateur (génération). Le code généré ne s'exécute que dans `kibo component test` / la validation, avec les restrictions de la phase 4 (imports interdits refusés au build, `bun test --preload restrict.ts` sans réseau, fichiers ni processus, SDK simulé) ; en phase 7, aussi dans le bac à sable OS.

## 8. Tests (zéro token)

- **Faux `claude`** (phase 2) étendu avec deux actions de scénario : `write { path, fixture }` (écrit un fichier via un événement `PreToolUse`/`PostToolUse` réaliste, soumis au garde-fou) et `result { json }` (sortie `--output-format json`). Fixtures dans `packages/daemon/src/testing/claude-scenarios/`.
- Scénarios :
  1. génération réussie du premier coup ⇒ `review` ⇒ finalisation ⇒ instance sur la page ;
  2. premier essai qui échoue au typecheck, second réussi (`--resume` avec le rapport) ;
  3. trois échecs ⇒ bouton « Corriger avec l'agent » désactivé ;
  4. tentative d'écriture de `kibo.component.json` et de `../evil.ts` ⇒ refusées par le hook ; modification directe détectée à `Stop` ⇒ restaurée ;
  5. code qui utilise `sdk.fetch` non déclaré ⇒ permission inférée et affichée à l'écran 30 ; argument non littéral ⇒ échec de validation ;
  6. onboarding : JSON valide ⇒ plan ; JSON invalide, composant inconnu, délai ⇒ preset.
- Unitaires : presets (composants absents retirés), calcul de version proposée, hash des fichiers réservés.
- e2e Playwright : écran 29 (IA) de bout en bout avec le faux `claude`, en sombre et en clair ; étape « Ton rôle » avec preset.

## 9. Critères de sortie

- Les scénarios 1 à 6 passent en CI macOS et Linux sans réseau ni token.
- Le composant généré par le faux agent est rendu sandboxé sur une page et passe la conformité.
- Écrans 29 (les deux colonnes) et 30 conformes en sombre et en clair ; étape « Ton rôle » conforme à sa maquette.

## 10. Écrans à dessiner dans Penpot avant implémentation

Étape « Ton rôle » du Nouveau projet (avec liste de pages cochables et état « Suggestion indisponible ») ; étapes 2 et 3 du dialogue écran 29 (run en cours, rapport de validation, échec après 3 tentatives, relecture du diff) ; saisie « Modifier avec l'IA ».

## 11. Hors périmètre

- Génération de `migrations.ts` par l'IA ; génération de composants dans le monorepo Kibo lui-même.
- Tout appel à l'API Anthropic avec une clé : seul l'abonnement via `claude` est utilisé.
- Assistant conversationnel général, résumé de tickets, génération de tickets (non prévus par la spec).

## 12. Décisions du plan

Décisions prises par le plan de la phase 6 (`docs/superpowers/plans/2026-09-26-kibo-ia.md`), qui priment sur le texte des sections précédentes en cas d'écart. I1 à I15 datent de l'écriture du plan ; I16 à I41 viennent de la réconciliation T0 avec le code livré des phases 2 à 5 (`main` à `191f171`).

- **I1 · Ports** : le métier IA (`packages/daemon/src/ai/`) ne dépend que de `ports.ts` ; le branchement sur le code réel est isolé dans une tâche. Raison : chaque module se teste avec des faux ports, sans `claude` ni réseau.
- **I2 · RPC ajoutées** à celles du §6 : `getAiStatus`, `getEnvironment` (écran 19), `listComponentDrafts` (reprendre un brouillon IA après fermeture du dialogue ; distinct de `listDrafts` de la phase 4, qui liste `components/src`), `reviewComponentDraft { draftId, version, changes }` (fin de relecture), `revalidateComponentDraft` (après une correction à la main), `openComponentDraftFolder`. `startComponentDraft` reçoit son entrée dans un champ `draft` ; `finalizeComponentDraft` reçoit en plus `strategy`. Les méthodes sont déclarées dans `packages/schema/src/ai-rpc.ts` (`AI_RPC`, comme `INTEGRATION_RPC`).
- **I3 · Permissions écrites avant la validation** : `inferPermissions` puis écriture dans le manifeste du brouillon, puis `validateComponent`. Raison : la validation de la phase 4 échoue sur `missing` non vide ; écrire après la ferait toujours échouer.
- **I4 · Délai de 60 s de l'assistant** compté depuis l'état `running`, pas depuis la mise en file ; en file, l'UI affiche « En file d'attente » et « Annuler ».
- **I5 · Lectures de l'agent confinées** au brouillon et aux sources de `@kibo/sdk` de la toolchain (`Read`, `Glob`, `Grep`). Raison : une lecture de `~/.ssh` finirait dans le contexte envoyé au modèle.
- **I6 · `server.ts` écrivable seulement si le brouillon a un backend** (case « Avec backend » ou `server.ts` présent dans la version de base).
- **I7 · Brouillon** : table `component_drafts` (base `kibo.db`) enrichie de `title`, `kind`, `withServer`, `failureJson`, `incidentsJson` ; base de comparaison dans `components/drafts/<draftId>.base/` (diff et restauration).
- **I8 · Forme de la config** : le manifeste étant réservé, l'agent ne peut pas la changer ; le contrôle « configSchema modifié : ajoute une migration » s'applique à `revalidateComponentDraft` (correction à la main) en mode `modify`.
- **I9 · Refuser à l'écran 30** ferme le dialogue sans perdre le brouillon (`permissions`, reprenable).
- **I10 · Modifier avec l'IA** : demande de 5 à 2000 caractères (c'est un delta) ; la finalisation refuse (`CONFLICT`) si `components/src/<id>` a changé depuis le début du brouillon.
- **I11 · Hors ligne** = `navigator.onLine === false` côté UI (événement du navigateur, déterministe).
- **I12 · Premier lancement** : l'écran 19 remplace la Vue d'ensemble tant qu'aucun projet n'existe ; « Importer un dossier existant » ouvre Nouveau projet avec le champ Dossier en focus.
- **I13 · Filtre « moi » du composant Tickets** (`configSchema.filter: "all" | "mine"`, défaut `all`, version du composant intégré inchangée) pour « Mes tickets » des presets.
- **I14 · Texte de l'écran 29** : « dans un worktree » devient « dans un dossier brouillon » (le brouillon n'est pas un worktree git) ; Penpot à mettre à jour.
- **I15 · Suggestion IA réservée au rôle « Autre »** (lecture du §5.1 étape 2) : « Décris ton usage » et « Proposer avec Claude » n'apparaissent que pour « Autre ».
- **I16 · Runs de l'IA = tâches sans ticket de la phase 2** : un run `assistant` ou `generateur` passe par `Orchestrator.submit(TaskInput)` (`ticketId: null`, `title` affiché dans la barre et le tiroir, `cwd`, `prompt` sur l'entrée standard, `extraArgs`, `env`, `resumeSessionId`, `guard`), donc par la file, ses créneaux et ses seuils. La sortie lue est `RunView.output` (ligne `result` brute du flux `stream-json`). `submit` n'est pas exposé en RPC : seul le démon lance ces runs. Raison : la phase 2 a livré exactement ce point d'extension (spec agents §3, §4).
- **I17 · Arguments de `claude`** : `--output-format stream-json`, `--permission-mode` (issu du profil, `default` ⇒ `manual` si la CLI ne connaît plus `default`) et `--permission-prompts none` restent fixés par le runner de la phase 2 (options réservées). L'IA n'ajoute que `--tools` (ou `--disallowedTools` de tous les outils sur une CLI ancienne), `--allowedTools "Bash(kibo component test:*)"`, `--disallowedTools "WebFetch,WebSearch"`, `--json-schema`, `--strict-mcp-config` et `--no-session-persistence` (assistant), selon les options détectées dans `claude --help`. La sortie structurée est lue dans `structured_output` de la ligne `result`, sinon dans `result` (texte, bloc ```` ```json ```` ou JSON nu). Remplace « `--output-format json` » du §5.1 étape 3.
- **I18 · Profils système** : `AgentProfile` gagne `system: boolean` (défaut `false`) et `enabled: boolean` (défaut `true`). Au démarrage, le démon crée (ou complète) dans le doc du workspace les profils d'identifiants fixes `assistant` (mode `default`, espace `isolated`, parallèle 1) et `generateur` (mode `acceptEdits`, espace `isolated`, parallèle 1), `subagents: []`. Seuls `model` et `enabled` sont modifiables ; un profil système ne se supprime pas et ne s'assigne pas à un ticket (`INVALID_INPUT`, et l'UI ne le propose pas). Modèle initial : celui du premier profil utilisateur (ordre alphabétique), sinon `sonnet`. Raison : la phase 2 n'a ni profil système ni profil « par défaut ».
- **I19 · Question de l'agent** : le garde-fou du générateur autorise l'outil MCP `mcp__kibo__ask_user` (question ⇒ `waiting_input` et champ « Répondre ») ; tout autre outil MCP est refusé.
- **I20 · Binaire `claude`** : le même que pour les agents (`--claude-bin` du démon, sinon `resolveClaudeBin` de la phase 2) ; `AGENT_CLI_NOT_FOUND` au sondage ⇒ `AiStatus.reason = "missing"`.
- **I21 · Événements** : `AiEvent` (`starter.ready`, `draft.changed`) rejoint l'union `ChangeMessage` du WebSocket, publiée par `docs.emit` ; le client gagne `subscribeAi(listener)` (même modèle que `subscribeIntegrations`, N24 de la phase 5).
- **I22 · Publication d'origine `ai`** : `Publisher.publish(id, strategy, { origin })` accepte une origine (défaut `user`, la RPC `publishComponent` est inchangée). Une version d'origine `ai` n'hérite jamais du niveau de confiance de la version précédente : l'écran 30 est toujours affiché. Raison : §7, « aucune confiance implicite parce que Kibo l'a généré ».
- **I23 · Finalisation** : `finalizeComponentDraft` installe les sources dans `components/src/<id>/`, publie (la phase 4 revalide et stocke), approuve (`RegistryService.approve`, qui applique « Mettre à jour partout » via `autoUpdate`), puis ajoute l'instance par `docs.run(addInstance)` ; elle renvoie `FinalizeResult { publish, version, instanceId }`. `TrustDialog` gagne une prop facultative `approve(trust)` qui remplace son appel à `approveComponent`, pour que l'écran 30 déclenche la finalisation.
- **I24 · Informations de publication = `PublishPreview`** (type de la phase 4) calculé depuis le brouillon (`validation` = rapport du brouillon, `migration: null`) ; l'étape 5 réutilise `UsagesBox`, `ChangesList` et `StrategyChoice` de l'écran 6.
- **I25 · Permissions utilisées = inférence ∪ usages de la conformité** : si la validation signale des permissions `missing` toutes de forme `read:`, `write:`, `data`, `net:` ou `mcp:`, Kibo les ajoute au manifeste et revalide une seule fois. Une URL relevée (`net:https://hôte/chemin`) devient la règle `hôte/chemin`, ou `hôte` si le chemin n'est pas une règle valide. Kibo n'ajoute jamais de `secret:` (un secret se déclare à la main) ni une écriture sans entité.
- **I26 · Dossier du brouillon** : ni lien `node_modules` (la validation travaille sur une copie liée à la toolchain), ni `.kibo/` (tampon de validation) ne comptent pour la restauration, le diff ou l'installation.
- **I27 · Commande `kibo` de l'agent** : `<KIBO_HOME>/bin/kibo`, script écrit au démarrage (binaire compilé : `exec <exécutable> "$@"`, le point d'entrée unique aiguille `component …` ; dev : `exec <bun> <dépôt>/packages/cli/src/bin.ts "$@"`, chemin calculé depuis les sources du démon), placé en tête du `PATH` du run ; le run reçoit aussi `KIBO_TOOLCHAIN` (la toolchain du démon), que la CLI lit pour valider. Aucune arête `cli ← daemon`.
- **I28 · Redémarrage pendant une génération** : la tâche d'un run sans ticket vit en mémoire (spec agents §4) ; au redémarrage, un brouillon `generating` annule son run s'il existe encore, passe `failed` (`interrupted`) et ses fichiers réservés sont restaurés. « Corriger avec l'agent » reprend la même session (`--resume`, l'identifiant de session est fixé par Kibo).
- **I29 · Chargement à la demande** : écran 19, dialogue « Suggérer des pages » et « Modifier avec l'IA » passent par `lazyPanel` ; le panneau IA de l'écran 29 vit dans le morceau différé d'« Ajouter un composant » ; les nouveaux fichiers rejoignent la liste des modules interdits dans l'entrée (`packages/ui/scripts/bundle-report.ts`). Budget du chargement initial inchangé (230 kB gzip).
- **I30 · Textes** : `packages/ui/src/i18n/fr-ai.ts` (`frAi` : clés `welcome`, `onboarding`, `ai`), étalé dans `fr`.
- **I31 · Pas de toast** : `sonner` reste hors de l'entrée (N29) ; les retours passent par l'état des dialogues. Création partielle d'un projet : le dialogue reste ouvert avec « Projet créé, mais certaines pages n'ont pas pu être ajoutées » et un bouton « Ouvrir le projet ».
- **I32 · Écran 19** : rendu par `ContentView` à la place de la Vue d'ensemble quand il n'y a aucun projet ni onglet ; « Connecter » ouvre l'onglet Paramètres › Intégrations.
- **I33 · Catalogue de départ** : l'assistant et les presets ne proposent que des composants sans configuration obligatoire : les intégrés `kanban`, `tickets`, `graph`, `notes` et les versions actives des composants `user` ou `ai` ; `mcp-source` (serveur à choisir à l'ajout) et les adaptateurs en sont exclus.
- **I34 · Diff d'un brouillon** : `git diff --no-index` lancé par `run` (`code/run.ts`, code 1 = différences) avec les options de diff de la phase 3, résultat passé à `parseDiff`, `hunkStaging: false` (lecture seule).
- **I35 · Ouvrir le dossier** : `editorCommand(dossier, null, env, plateforme)` puis `openInEditor` de la phase 3 (`EDITOR_UNAVAILABLE` sinon).
- **I36 · Capacité de l'écran 19** : `HostView` de la file (`cores`, `ramGb`, `hostSlots`) ; GitHub connecté = état `connected` de `github` dans `listIntegrations`.
- **I37 · Environnement des runs en test** : `DaemonOptions.agentEnv` (environnement de base des runs d'agent et du sondage de `claude`, par défaut `process.env`), utilisé par les tests d'intégration pour le faux `claude` ; l'E2E passe par l'environnement du processus du démon (`e2e/serve.ts`), sans nouveau drapeau.
- **I38 · Type d'un brouillon** : `widget`, `view` ou `both` (le type `adapter` du manifeste est exclu).
- **I39 · Faux `claude`** (`packages/daemon/src/agents/fake-claude.ts`) étendu : étape `write { path, fixture, bypassHooks? }` (hooks `PreToolUse` puis `PostToolUse` réels, écriture refusée si le hook refuse), `structuredOutput` d'un tour (ajouté à la ligne `result`), réponses à `--version`, `--help` (aide de la 2.1.283 ou ancienne) et `auth status --json`. Scénarios dans `packages/daemon/src/agents/scenarios/ai/`, fixtures dans son sous-dossier `fixtures/`, suffixées `.fixture` quand elles ont une extension de code (`ui.tsx.fixture`, `evil.ts.fixture`) pour rester hors du lint et du typecheck. Remplace « `result { json }` » et l'emplacement `testing/claude-scenarios/` du §8.
- **I40 · Identifiant réservé** : un `id` de brouillon `create` est refusé (`CONFLICT`) s'il est intégré, publié, présent dans `components/src/` ou porté par un autre brouillon actif.
- **I41 · Sortie de l'assistant en file** : un run de l'assistant encore en file au redémarrage échoue (tâche perdue) sans effet ; l'UI a déjà retenu « indisponible » à la coupure du WebSocket (aucun `starter.ready` attendu après reconnexion).
- **I42 · Intégrité de la base du brouillon** (décision du lead) : pas d'empreinte de `<draftId>.base/` en base de données. Un code capable d'écrire dans la base a échappé au confinement et peut aussi réécrire `kibo.db` ou tout fichier de l'utilisateur ; l'empreinte ne protégerait rien. La base repose sur le confinement : le hook `PreToolUse` (T3) compare les chemins avec `path.relative` (jamais un préfixe de chaîne, car `<draftId>.base` commence comme `<draftId>`), `Bash` se limite à `kibo component test .` sous les restrictions de la phase 4, puis le bac à sable OS en phase 7. La publication reste protégée par la validation, l'empreinte et l'écran 30.
- **I43 · Un brouillon actif par composant** (décision du chef d'équipe) : un composant a au plus un brouillon actif, création ou modification ; `newDraft` refuse un second brouillon (`CONFLICT`), qu'il vise un composant publié ou un identifiant réservé.
- **I44 · Source à l'abandon** (décision du chef d'équipe) : abandonner un brouillon dont la version a été publiée garde la nouvelle source ; une version non publiée remet la sauvegarde (`modify`) ou libère l'identifiant (`create`), seulement si la source installée est bien celle du brouillon (même `id` et même `version` de manifeste).
- **I45 · Relecture depuis permissions** (décision du lead) : `reviewComponentDraft` est aussi accepté en `permissions` ; il réécrit `version` et `changes` du manifeste (version strictement supérieure à la dernière publiée) sans changer d'état, et l'empreinte à présenter change avec le manifeste. C'est la sortie d'une version `ai` déjà publiée avec d'autres sources (empreinte refusée après publication) : `finalizeComponentDraft` répond `VERSION_EXISTS` et invite à relire avec une version supérieure ; une version `ai` identique à l'empreinte relue reprend la finalisation. La finalisation est exclusive par composant : une seconde finalisation concurrente du même `componentId` est refusée (`CONFLICT`). La version orpheline reste dans le registre, sans nettoyage automatique.
- **I46 · Dialogues pendant l'approbation** (décision du chef d'équipe) : pendant l'approbation d'un composant généré (écran 30), seul le dialogue de confiance est visible ; les dialogues Ajouter un composant et Créer un composant sont masqués (pas démontés : leur état est gardé) et réapparaissent sur Refuser ; Autoriser et ajouter les ferme. Refuser (ou Échap) ramène le brouillon à la relecture du diff ; « J'ai relu, continuer » rouvre alors le dialogue de confiance sans appel au démon. La même règle s'applique à « Modifier avec l'IA ».

## 13. Décisions de la phase 9, vague 4 (lot 9 : créations en arrière-plan, images, aperçu, contexte)

Écrites le 2026-10-01 avec la spec de conception §16 et la spec composants §17 ; elles amendent §4.2, §5.2, §6 et I18 sans changer le cycle d'un brouillon ni ses garde-fous (§7).

1. **Brouillons en arrière-plan et en parallèle** : un brouillon est déjà un run de la file (I16) ; fermer le dialogue ne l'arrête pas (le brouillon et son run continuent, l'état vit dans `component_drafts` et dans la file). Zéro token : l'état vient de `draft.changed` (I21) et de l'état des runs (`getAgents`).
4. **Images jointes** : `StartComponentDraftInput` (`create` et `modify`) et `reviseComponentDraft` acceptent `attachments: DraftAttachmentInput[]` (0 à 4, `MAX_DRAFT_ATTACHMENTS`) avec `{ name, mime, data }` : nom de 1 à 64 caractères (`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`), `mime` et `data` comme `IconInput` (PNG, JPEG, WebP ; 256 kB décodés ; base64 canonique ; signature vérifiée par `decodeIcon` : `INVALID_INPUT` si discordance, `TOO_LARGE` au-delà).
